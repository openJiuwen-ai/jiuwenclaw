# Plugin Audit — 插件代码安全审计

## Overview

在用户安装 OpenClaw 插件之前，对插件源码进行安全审计。检测恶意代码模式并输出风险报告，由用户自行决定是否安装。

**核心原则：** 审计结果仅供参考和告警，不做强制拦截。最终决定权在用户。

## Trigger Condition

**自动触发** — 当用户请求中包含以下意图时，本 skill 必须被加载使用：

| 触发场景 | 示例用户表达 |
|---------|------------|
| 安装插件 | "帮我安装 xxx 插件"、"装一个 xxx 插件" |
| 搜索插件并安装 | "帮我找个 xxx 插件装上" |
| 从市场安装 | "帮我装这个 clawhub:xxx" |
| 从 GitHub 安装 | "装上这个 GitHub 插件" |
| 从本地安装 | "帮我装这个 /path/to/plugin" |
| 审计已有插件 | "帮我看看这个插件有没有毒"、"审计这个插件" |

**不触发场景：** 纯搜索不安装、仅查看插件列表、启用/禁用已有插件。

## Workflow

```
用户请求安装插件
    │
    ▼
1. 解析插件来源 (npm / git / 本地 / 压缩包)
    │
    ▼
2. 获取插件源码到临时目录
    │
    ▼
3. 运行静态代码审计 (audit-plugin.py)
    │  → 正则规则扫描，输出结构化报告
    ▼
4. 代码补充审查（脚本覆盖不到的部分）
    │  → 由模型通读源码，关注脚本规则无法检测的逻辑：
    │    - 字符串拼接/动态构建的恶意 URL
    │    - 通过环境变量或配置文件注入的行为
    │    - 使用反射、Proxy、setter 隐藏的恶意调用
    │    - 新型或变种的混淆/编码方式
    │    - 规则语义匹配不上的异常逻辑
    │    - 任何看起来不对劲的代码模式
    ▼
5. 输出最终审计报告
    │  → 汇总脚本结果 + 模型审查发现，给用户完整判断
    ▼
6. 用户自行决定是否继续安装
```

### 双层审计机制说明

#### 第一层：脚本静态扫描（audit-plugin.py）

正则规则扫描，快速检测明确的恶意模式。优点：确定性强、无遗漏、不遗漏高危关键词。
局限性：只能匹配预设规则，对混淆、编码、间接调用等手法可能漏报。

#### 第二层：模型代码审查（模型人工审阅）

脚本结果出来后，模型**必须**对插件源码做一次全面审阅，重点涵盖：

| 审查要点 | 说明 |
|---------|------|
| 脚本漏报的疑似行为 | 规则没匹配到但模型觉得可疑的代码 |
| 间接恶意调用 | 通过回调、事件监听、定时器延迟执行的恶意操作 |
| 语义级异常逻辑 | 代码整体意图与插件功能声明不符（比如一个 Markdown 插件在读取 SSH 密钥） |
| 数据流分析 | 敏感数据（token、路径、系统信息）是否在代码中流动并有外传路径 |
| 依赖利用 | require 了危险的库但没在代码里明显使用（可能是动态调用） |
| 字符串拼接/动态构造 | 用变量拼接 URL、命令、路径等，脚本无法命中但模型可以判断意图 |
| 隐藏通道 | 利用 DNS、定时请求、日志上报等隐蔽方式回传数据 |
| 时间触发行为 | setTimeout/setInterval/process.nextTick 延迟执行的代码 |
| 错误处理隐藏逻辑 | catch 块中执行额外操作（静默外传） |

**审查方式：** 模型读取插件目录下的关键源码文件（入口文件、主要逻辑文件、package.json scripts），逐文件人工评估。对于小型插件（< 10 个文件）应全部审阅，大型插件优先审阅入口、网络请求、文件操作相关文件。

**补充发现处理：** 模型审查发现的额外问题，以相同格式追加到审计报告中，来源标记为 `[模型审查]`。

### 强制执行规则（必须遵守）

以下规则为**刚性约束**，任何情况下不得省略或跳过：

#### 规则 A：必须先输出审计报告，再执行安装
- 在步骤 5（输出最终审计报告）完成后，**必须将完整审计报告以消息形式回复给用户**
- 必须清晰展示：扫描文件数、风险评级、脚本发现问题、模型审查补充发现
- 不得在输出报告前直接调用安装命令

#### 规则 B：必须等待用户确认，再安装
- 在步骤 6（用户自行决定是否继续安装）中，**必须明确询问用户是否继续安装**
- 无论审计结果是 🟢、🟡 还是 🔴，都**必须**等待用户明确表态后再执行安装
- 用户确认前，不得执行任何安装命令
- 即使审计结果为 🟢 安全，也应询问："审计通过，可以正常安装。是否继续安装？"

#### 规则 C：违规后的补救措施
- 如果安装已经完成但未执行审计流程 → 需卸载插件，按完整流程重新执行一遍
- 不得以"代码我读过了是安全的"为由跳过结构化输出和确认环节

### 步骤详解

#### 1. 解析插件来源

根据用户输入判断插件来源：

| 来源 | 识别方式 | 传递参数 |
|------|---------|---------|
| npm 包 | `npm:x/xxx`、`@scope/xxx`、纯包名 | `--npm <package>` |
| GitHub | `github.com/...`、`git@...`、`https://...git` | `--git <url>` |
| 本地路径 | 绝对路径或 `./xxx` | `--dir <path>` |
| 压缩包 | `.zip/.tar.gz/.tgz` 路径 | `--archive <path>` |

#### 2. 获取源码

- **npm 包**：`npm pack --pack-destination <tmp>` 下载 + 解压
- **GitHub**：`git clone --depth=1 <url>` 到临时目录
- **本地目录**：直接使用
- **压缩包**：解压到临时目录

#### 3. 运行审计

```bash
python3 <skill-dir>/audit-plugin.py <source-dir> --name <plugin-name> [--json]
```

#### 4. 输出审计报告

风险评级（综合脚本 + 模型审查结果）：

| 评级 | 标识 | 含义 |
|------|------|------|
| 🟢 安全 | safe | 脚本 + 模型审查均未发现可疑模式 |
| 🟡 可疑 | suspicious | 脚本或模型审查发现可疑模式，需要用户确认 |
| 🔴 高危 | critical | 发现高危恶意模式，强烈建议不要安装 |

报告结构示例：

```
═══════════════════════════════════════════
  🔍 插件安全审计报告
═══════════════════════════════════════════
  插件名称: xxx-plugin
  扫描文件: 27 个
  风险评级: 🟡 可疑
───────────────────────────────────────────
  [脚本扫描] 发现 2 项问题:
  ⚠️ SR-005 Shell 命令执行 → src/utils.js:45
  ⚠️ SR-001 动态代码执行 → src/index.js:132

  [模型审查] 发现 1 项补充:
  ⚠️ src/setup.js 中 setTimeout 延迟执行 exec，
     脚本可能漏报，代码意图可疑
───────────────────────────────────────────
  是否继续安装此插件？
```

## Script Location

审计脚本位于 skill 目录下：

```
<skill-dir>/audit-plugin.py
<skill-dir>/patterns/high-risk.json      # 高危规则
<skill-dir>/patterns/medium-risk.json    # 可疑规则
```

## 恶意模式清单

### 🔴 高危（直接阻止安装建议）

规则文件：`patterns/high-risk.json`

| 编号 | 模式 | 说明 |
|------|------|------|
| HR-001 | 读取配置并外传 | 同时存在读取本地配置文件和网络外传 |
| HR-002 | 反连/数据外传 | 向非预期外部地址发请求 |
| HR-003 | 密钥/凭证窃取 | 读取 SSH 密钥、API Token 等凭证文件 |
| HR-004 | 持久化后门 | 写入 cron、bashrc、systemd 等 |
| HR-005 | 硬编码恶意载荷 | base64 编码 + eval/exec 执行 |
| HR-006 | 环境变量批量偷取 | 读取全部 env 并外传 |

### 🟡 可疑（需用户确认）

规则文件：`patterns/medium-risk.json`

| 编号 | 模式 | 说明 |
|------|------|------|
| SR-001 | 动态代码执行 | eval / Function / vm 动态执行 |
| SR-002 | 代码严重混淆 | 高 entropy 变量名、大量编码 |
| SR-004 | 大范围文件写入 | 在插件目录外写入文件 |
| SR-005 | Shell 命令执行 | child_process 调用系统命令 |
| SR-006 | 网络请求+路径拼接 | 从网络下载并写入本地 |
| SR-007 | 动态 require | 变量拼接模块路径 |
| SR-008 | 删除文件 | 调用 unlink/rm 等 |

## 安装建议

根据审计结果向用户给出明确建议：

- **🟢 安全** → "审计通过，可以正常安装。是否继续安装？"
- **🟡 可疑** → "发现 X 项可疑内容，建议确认来源可信后再安装。是否继续安装？"
- **🔴 高危** → "检测到 X 项高危风险，强烈建议不要安装此插件。如果你坚持安装，请知悉风险。"

## 注意事项

1. 本 skill **不拦截安装命令**，只做审计报告输出，最终决定权在用户。
2. 审计范围**仅限插件自身源码**，不递归扫描 `node_modules` 依赖树。
3. 如果安装来源无法获取源码（如仅有二进制），提示用户来源不可审计。
4. 审计结果作为参考依据，不能 100% 保证安全。用户应结合可信度判断。
5. 临时目录在审计完成后自动清理。
