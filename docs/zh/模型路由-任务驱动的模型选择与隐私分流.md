# 模型路由：任务驱动的模型选择与隐私分流

---

## 概念科普

### 模型路由是什么

模型路由（Model Routing）是 JiuwenSwarm 在多模型环境下提供的任务适配与隐私保护系统。它解决两个核心问题：**选谁干** 和 **敏感信息往哪送**。

- **分数路由**解决"选谁干"：根据任务类型和难度算出目标分数，在能力表里选 model_score 最接近的模型——重活选强模型，轻活选弱模型，避免大马拉小车或小马拉大车。
- **隐私分流**解决"敏感信息往哪送"：检测到隐私内容（身份证、密码、银行卡等）时，优先路由到标记 `is_trusted` 的可信模型；无可信模型则直接取消请求，防止敏感数据流向不可控端点。

可以把模型路由理解为"三段式安检 + 智能派单"：**单模型跳过 → 隐私分流 → 分数路由**。如果只有一个模型可选，路由自动跳过（没得选就不选）；如果启用隐私检测且命中隐私，优先送可信模型；正常情况下按分数最近匹配派给最合适的模型。

#### 分数路由怎么派单

分数路由的核心是 **目标分数 → 最近匹配**：

1. 分类器根据用户 prompt 判断任务类型（category）和难度（difficulty），给出原始分数（raw_score）。
2. 从分数表（score_table）查 `(category, difficulty)` 的精确分数；查不到则按难度取默认分数（easy=10, medium=30, hard=50）；如果分类器给出的难度不在(easy, medium, hard)的范围内，则取默认分数为 50。
3. **Hard 难度特长约束**：如果难度为 hard，优先把候选范围缩小到 `model_expertise_category` 含该任务 category 的模型。例如 coding/hard 只选标了 coding 专长的模型。无专长匹配时兜底回全表（与 vision 约束同样的 fallback 策略）。
4. 在候选里选 `model_score` 最接近目标分数的模型；等距时偏高分（质量优先）。

例如：用户问"帮我写一段 Python 代码"，分类器判断 coding/hard → 目标分数 90 → 先限到标了 coding 专长的模型 → 在这些模型里选 model_score 最接近 90 的；用户问"帮我排版这段文字"，分类器判断 format/easy → 目标分数 10 → 不触发特长约束（easy 不受约束）→ 全表选最接近 10 的小模型（更省成本）。

#### 为什么 hard 任务要走特长约束

medium/easy 任务对模型专长的要求不高——通用模型也能做格式化、简单总结。但 hard 任务往往需要深度理解：coding/hard 要写出复杂算法，reasoning/hard 要严密推理链。如果只按分数匹配，一个 score=90 的通用聊天模型可能被选中，但它未必擅长写代码。

特长约束确保 hard 任务优先交给**声称擅长该领域的模型**。如果一个模型标了 `model_expertise_category=["coding", "reasoning"]`，说明它在编程和推理上有专门优化；coding/hard 的请求就会优先路由到它，而不是一个分数相近但只会聊天的通用模型。

无模型标了对应专长时，兜底回全表——不做空约束，让分数路由在所有候选里选最近的。

#### 隐私分流怎么保护

隐私分流在分数路由之前执行，属于硬约束——命中隐私时，分数路由不再参与，直接选可信模型或取消请求：

- 命中隐私 + 有 `is_trusted` 模型 → 选最强可信模型（按 model_score 排序取最高）。
- 命名隐私 + 无 `is_trusted` 模型 → 直接取消请求，给用户留提示消息，不把敏感内容送到任何模型。

隐私正则来自 `model_routing_privacy.json`，覆盖常见敏感信息：密码/密钥、中文隐私关键词、身份证号、手机号、Bearer Token、邮箱地址。

#### 含图请求怎么处理

当请求包含图片输入时，候选模型硬约束到 `model_type=="vision"` 的视觉模型；非含图请求则排除视觉专用模型。这是类型约束，与分数路由叠加——先过滤类型，再在候选里做分数匹配。

#### 它解决什么问题

| 问题 | 传统做法 | 模型路由的做法 |
|------|---------|--------------|
| 重活轻活都给同一个模型 | 手动切换或固定最强模型 | 按分数自动选——重活选强，轻活选弱 |
| Hard 任务给了不擅长的模型 | 不区分专长，按分数/品牌随便选 | hard → expertise 约束 → 选声称擅长该领域的模型 |
| 多 API 同模型怎么区分 | 不区分，token 统计串账 | client_id 按(api_base+api_key)派生哈希，独立记账 |
| 敏感信息流向不可控端点 | 不管控，全送默认模型 | 隐私命中 → 只送可信模型；无可信 → 取消 |
| 视觉请求给了纯文本模型 | 不区分，可能选错 | 含图 → 约束到 vision 模型 |
| 模型能力参数分散在各处 | config 硬编码 | 外置 JSON（capability_map/privacy/mapper），用户可自定义覆盖 |

### 基本工作流

```text
启动 → 加载能力表 + 分类器 + 隐私正则 + 分数表
  ↓
用户请求到达
  ↓
[安检 1] 单模型跳过？
  ├─ 是 → 直接输出唯一模型，不走后续
  └─ 否 ↓
[安检 2] 隐私命中？
  ├─ 是 → 有 trusted？选最强可信模型 / 无 trusted？取消请求
  └─ 否 ↓
[正常路由] 分类器 → (raw_score, category, difficulty)
  ↓
task_score(category, difficulty, mapper) → 目标分数
  ↓
[约束 1] hard 难度特长约束（difficulty=="hard" 时优先选 expertise 匹配的模型；无匹配→全表兜底）
  ↓
[约束 2] 类型约束（含图→vision / 非含图→排除 vision）
  ↓
model_score 最近匹配 → 推荐模型
  ↓
apply_routing=True？set_llm 切换模型 / 否：只推荐不切
```

### 运行时行为

模型路由作为 DeepAgentRail 运行，优先级 95，在每次模型调用前自动执行。用户不需要手动触发——只要配置了 `model_routing.enabled`，所有请求都会经过路由。

路由完成后，决策结果写入 `ctx.extra["model_routing_decision"]`，包含：

| 字段 | 说明 |
|------|------|
| `recommended_model_id` | 推荐模型的 client_id |
| `analysis` | TaskAnalysis：category、difficulty、target_score、predicted_input_tokens |
| `reasoning` | 路由推理过程（"classifier score=90; score match: target=90 → big-model(score=90)"） |
| `prior_calls_otel` | 本次 invoke 内前置调用的 OTel span 列表 |
| `model_usage_stats` | 当前 token 统计快照 |
| `privacy_hit` | 是否命中隐私分流 |

## 操作指导

### 1. 准备模型配置

模型路由依赖两个前提：

- **config.yaml 里配置了多个模型**：`models.defaults` 至少包含 2 个模型条目（含 `model_client_config`）。只有 1 个模型时路由会自动跳过。
- **模型能力表文件就绪**：`routing_state/model_capability_map.json` 已存在（首次启动会从包内模板自动拷贝）。

模型配置方式见 [配置信息](配置信息.md)。

### 2. 开启模型路由

操作路径：

```text
左侧导航栏 → 配置信息 → 模型路由
```

打开 **启用模型路由** 后保存配置。

相关配置项：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `model_routing.enabled` | `false` | 是否启用模型路由 |
| `model_routing.apply` | `false` | 路由结果是否真切换模型（`set_llm`）；`false` 时只推荐不切 |
| `model_routing.privacy_check` | `false` | 是否启用隐私检测分流 |
| `model_routing.stats_path` | 空字符串 | 统计文件路径；为空时使用默认位置 |

开启后，每次模型调用前会自动执行路由。关闭后回到原有行为——所有请求使用默认模型。

> **提示**：`apply=false` 是安全的起步方式——路由只给出推荐结果，不实际切换模型，适合观察路由效果后再决定是否开启真切换。

### 3. 配置可信模型

隐私分流需要至少一个标记 `is_trusted` 的模型。在 `config.yaml` 的模型条目中设置：

```yaml
models:
  defaults:
    - model_client_config:
        model_name: GLM-5.1
        client_provider: DashScope
        api_key: "你的密钥"
        api_base: "https://..."
      is_trusted: true          # ← 标记为可信模型
    - model_client_config:
        model_name: deepseek-chat
        client_provider: DeepSeek
        api_key: "你的密钥"
        api_base: "https://..."
      # 不标记 is_trusted → 隐私命中时不选此模型
```

- **`is_trusted: true`**：隐私命中时，此模型可接收敏感数据。多 trusted 模型时选最强（model_score 最高）。
- **不标记或 `is_trusted: false`**：隐私命中时不选此模型。

> **注意**：可信标记应仅用于数据合规可控的模型（如私有部署、合规云服务），不应标记给数据流向不透明的公共 API。

### 4. 配置视觉模型

含图请求需要至少一个 `model_type: vision` 的模型。在模型条目中设置：

```yaml
models:
  defaults:
    - model_client_config:
        model_name: GLM-5.1
        ...
      # 普通文本模型（默认 model_type=""）
  vision:
    model_client_config:
      model_name: qwen-vl-max
      client_provider: DashScope
      api_key: "你的密钥"
      api_base: "https://..."
      # vision 专用模型，含图请求时参与路由
```

也可以在 `models.defaults` 条目上直接标 `model_type: vision`：

```yaml
models:
  defaults:
    - model_client_config: {...}
      model_type: vision       # ← 标记为视觉模型
```

视觉模型在非含图请求时会被排除；含图请求时只选视觉模型（无视觉模型则用全表兜底）。

### 5. 配置模型专长

Hard 难度的任务会优先路由到声称擅长对应领域的模型。在模型条目中通过 `model_expertise_category` 标记专长：

```yaml
models:
  defaults:
    - model_client_config:
        model_name: deepseek-coder-v2
        client_provider: DeepSeek
        api_key: "你的密钥"
        api_base: "https://..."
      model_expertise_category: ["coding"]    # ← 标记编程专长
    - model_client_config:
        model_name: GLM-5.1
        client_provider: DashScope
        api_key: "你的密钥"
        api_base: "https://..."
      model_expertise_category: ["reasoning", "coding"]  # ← 标记推理+编程专长
    - model_client_config:
        model_name: qwen3-max
        ...
      # 不标记 expertise → hard 任务时不在特长候选里
```

专长标记的效果：

| 场景 | 无专长标记 | 有专长标记 |
|------|-----------|-----------|
| coding/hard | 全表按分数选（通用模型可能被选中） | 先限到标了 coding 的模型 → 再按分数选 |
| reasoning/hard | 同上 | 先限到标了 reasoning 的模型 → 再按分数选 |
| chat/easy / format/medium | **不受约束**——全表按分数选 | **不受约束**——easy/medium 不触发特长筛选 |
| 无模型标了对应专长 | — | 兜底回全表，不做空约束 |

> **调整建议**：如果你的模型确实在某个领域有优势（如 DeepSeek-Coder 在编程、Claude 在推理），建议标记对应专长。Hard 任务会优先路由到它，避免通用聊天模型抢了需要深度理解的请求。

也可以在 `model_capability_map.json` 的 `models` 字段中覆盖：

```json
{
  "models": {
    "deepseek-coder-v2": {"model_score": 80, "model_expertise_category": ["coding"]},
    "GLM-5.1": {"model_score": 57, "model_expertise_category": ["reasoning", "coding"]}
  }
}
```

### 6. 自定义分类器和分数表

分类器和分数表由 `classifier_mapper.json` 控制。首次启动时从包内模板拷贝到用户目录：

```text
~/.jiuwenswarm/config/routing_state/classifier_mapper.json
```

#### 分数表

`score` 字段定义 `(category, difficulty)` 到目标分数的映射：

```json
{
  "score": {
    "chat.easy": 5,
    "chat.medium": 20,
    "chat.hard": 45,
    "coding.easy": 15,
    "coding.medium": 40,
    "coding.hard": 65,
    "reasoning.hard": 55,
    "summarization.medium": 30,
    "format.easy": 5
  }
}
```

- 格式：`"category.difficulty"` → 整数分数。
- 分数越高 → 选越强的模型；分数越低 → 选越弱的模型。
- 未覆盖的组合按难度默认分：easy=10, medium=30, hard=50。

> **调整建议**：如果轻任务总是选到大模型，适当降低对应分数（如 `"format.easy": 5→3`）；如果重任务选到弱模型，适当提高分数（如 `"coding.hard": 65→85`）。

#### 分类器

`classifier` 字段定义分类器的行为。当前使用 **文本注入** 方式——`source` 是 `async def classify(prompt_text)` 的函数体文本，被 exec 编译为异步函数：

```json
{
  "classifier": {
    "imports": ["re", "json"],
    "source": "source 函数体文本...",
    "extras": {
      "api_base": "分类器专用模型 API 地址",
      "api_key": "分类器专用模型密钥",
      "model_name": "分类器模型名",
      "client_provider": "OpenAI",
      "temperature": 0,
      "system_prompt": "分类提示词"
    }
  }
}
```

- `imports`：注入到 exec namespace 的模块列表。
- `source`：函数体文本，返回 `(raw_score, category, difficulty)` 三元组。
- `extras`：注入 `_EXTRAS` dict，source 内可引用（如 `_EXTRAS["api_base"]`）。

分类器 source 内可引用的注入数据：

| 变量 | 类型 | 说明 |
|------|------|------|
| `_EXTRAS` | `dict` | classifier.extras 字段 |
| `_CATEGORIES` | `tuple` | categories 列表 |
| `_DIFFICULTIES` | `tuple` | difficulties 列表 |
| `_SCORE_TABLE` | `dict` | `{(cat, diff)→int}` 分数表 |
| `_DEFAULT_SCORE` | `dict` | `{diff→int}` 默认分 |

工具函数不自动注入——source 需要时自行 import：

```python
from jiuwenswarm.agents.harness.common.rails.model_routing.classifier import (
    _build_llm_model, _parse_classifier_response, _lookup_score
)
```

#### 无分类器时的行为

如果 `classifier_mapper.json` 缺少 `classifier` 字段，或分类器加载失败，路由会 fallback 到 `(raw_score=50, category="unknown", difficulty="hard")`。此时目标分数固定为 50，选 model_score 最接近 50 的模型。这保证了即使分类器不可用，路由仍能产出决策——只是不区分任务轻重。

### 7. 自定义隐私正则

隐私正则由 `model_routing_privacy.json` 控制：

```text
~/.jiuwenswarm/config/routing_state/model_routing_privacy.json
```

```json
{
  "patterns": [
    {"label": "credentials", "regex": "(?:password|secret|token|api_key|apikey)..."},
    {"label": "chinese_privacy", "regex": "身份证|密码|银行卡..."},
    {"label": "chinese_id", "regex": "\\d{6}(?:19|20)\\d{2}..."},
    {"label": "phone", "regex": "1[3-9]\\d{9}"},
    {"label": "bearer_token", "regex": "Bearer [A-Za-z0-9._-]+"},
    {"label": "email", "regex": "[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+..."}
  ]
}
```

- 每条正则含 `label`（标识）和 `regex`（正则表达式字符串）。
- 任一正则命中 → 触发隐私分流。
- 用户可在 `routing_state` 目录修改此文件，添加或调整正则。修改后下次启动生效。

> **注意**：正则过宽可能导致正常对话被误判为隐私命中。建议调试时先开启 `privacy_check=true` 但 `apply=false`，观察日志里的 `PRIVACY-HIT` 标记，确认正则命中率后再决定是否开启真切换。

### 8. 自定义模型能力映射

模型能力映射由 `model_capability_map.json` 控制，包含两部分：

- **vendor_map**：model_name 子串 → (model_group, model_provider) 的前缀映射（22 条默认）。
- **models**：model_name 精确匹配 → 能力字段覆盖（约 70 条默认），主要覆盖 `model_score`。

```text
~/.jiuwenswarm/config/routing_state/model_capability_map.json
```

```json
{
  "vendor_map": [
    {"prefix": "glm", "group": "GLM", "provider": "zhipu"},
    {"prefix": "qwen", "group": "Qwen", "provider": "alibaba"}
  ],
  "models": {
    "GLM-5.1": {"model_score": 57},
    "deepseek-chat": {"model_score": 35}
  }
}
```

如果配置了模型能力表未覆盖的模型或者有自主训练的特制模型，`model_score` 也可以在 `config.yaml` 的模型条目中设置：

```yaml
models:
  defaults:
    - model_client_config:
        model_name: GLM-5.1
        client_provider: DashScope
        api_key: "你的密钥"
        api_base: "https://..."
      model_score: 55          # ← 手动设置 model_score
    - model_client_config:
        model_name: deepseek-chat
        client_provider: DeepSeek
        api_key: "你的密钥"
        api_base: "https://..."
      # 不设置 model_score → 会按照 model_capability_map.json 映射
```

`model_score` 是路由的核心分数。调整模型 score 会直接影响路由选择：

- score 越高 → 越容易被重任务选中。
- score 越低 → 越容易被轻任务选中。
- 等距时偏高分（质量优先）。

> **调整建议**：如果某个模型总是不被选中，检查它的 `model_score` 是否与任务分数差距过大。可以在 `models` 字段中精确覆盖该模型的 score。

### 9. 查看路由日志

路由过程通过日志输出，可在服务端日志中观察：

```text
[ModelRouting] classifier: [coding,hard] score=90 in_tok=4 privacy=False -> recommend=big
[ModelRouting] classifier: [format,easy] score=10 in_tok=2 privacy=False -> recommend=small
[ModelRouting] skipped (single model); in_tok=4
[ModelRouting] PRIVACY-HIT: session=xxx caps=2 trusted=1 prompt_preview='my password...'
[ModelRouting] privacy hit -> trusted model big-model
[ModelRouting] PRIVACY-CANCEL (no trusted): session=xxx -> cancel + leave message
[ModelRouting] applied set_llm -> GLM-5.1
```

| 日志关键字 | 含义 |
|-----------|------|
| `classifier: [...]` | 正常路由：分类结果、目标分数、推荐模型 |
| `skipped (single model)` | 单模型跳过 |
| `PRIVACY-HIT` | 隐私命中 |
| `privacy hit -> trusted model` | 隐私命中，选可信模型 |
| `PRIVACY-CANCEL (no trusted)` | 隐私命中但无可信模型，取消请求 |
| `applied set_llm ->` | 真切换模型 |

## 配置说明

### 配置项总览

```yaml
model_routing:
  enabled: true             # 启用模型路由
  apply: false              # 路由结果是否真切换模型
  privacy_check: false      # 是否启用隐私检测
  stats_path: ""            # 统计文件路径（为空用默认位置）
```

### `model_routing.enabled`

是否启用模型路由。默认 `false`。

开启后，每次模型调用前会执行路由逻辑。关闭后回到原有行为——所有请求使用默认模型，不做分类、隐私检测或模型选择。

### `model_routing.apply`

路由结果是否真切换模型（`set_llm`）。默认 `false`。

- `false`：路由只产出推荐结果和决策信息，不切换模型。适合观察路由效果。
- `true`：路由后会实际切换 agent 当前模型到推荐模型，并同步 config 里的 `model_name`、`model_client_config`、`model_config_obj`。后续模型调用会使用路由后的模型。

> **注意**：开启 `apply=true` 后，所有请求都会被路由到推荐模型。建议先在 `apply=false` 模式下观察路由日志，确认路由选择合理后再开启真切换。

### `model_routing.privacy_check`

是否启用隐私检测分流。默认 `false`。

- `false`：跳过隐私检测，所有请求走正常分数路由。
- `true`：在分数路由前执行隐私检测。命中隐私 → 选可信模型或取消请求。

> **注意**：隐私检测依赖正则匹配，可能误判。建议先开启 `privacy_check=true` 但 `apply=false`，观察日志中的 `PRIVACY-HIT` 标记，确认正则命中率后再决定是否开启真切换。

### `model_routing.stats_path`

模型统计文件的存储路径。为空时使用默认位置：

```text
~/.jiuwenswarm/config/routing_state/model_routing_list.json
```

统计文件记录每个模型的 token 使用量（input/output/call_count/last_used），跨会话累积。路由启动时合并已有统计到能力表，热重载时回写整表。

### 附：完整配置项示例

```yaml
model_routing:
  enabled: true
  apply: true                # 真切换模型
  privacy_check: true        # 启用隐私分流
  stats_path: ""             # 使用默认路径

  # 以下为旧版配置字段，新版已废弃——分类器由 classifier_mapper.json 外置
  # classifier:              # ← 不再使用
  #   api_base: ...
  #   api_key: ...
  #   model_name: ...
```

### 外置 JSON 配置文件

三个 JSON 文件存放在 `routing_state` 目录，首次启动从包内模板自动拷贝，用户可修改覆盖：

```text
~/.jiuwenswarm/config/routing_state/
├── classifier_mapper.json      分类/难度/分数表 + 分类器配置
├── model_capability_map.json   厂商前缀映射 + 模型 score 覆盖
├── model_routing_privacy.json  隐私正则配置
├── model_routing_list.json     token 统计（自动生成，不要手动改）
```

#### `classifier_mapper.json`

| 字段 | 类型 | 说明 |
|------|------|------|
| `categories` | `list[str]` | 任务分类列表（chat/reasoning/coding/summarization/format） |
| `difficulties` | `list[str]` | 难度列表（easy/medium/hard） |
| `score` | `dict` | `"category.difficulty"` → 目标分数 |
| `classifier.imports` | `list[str]` | 注入到 exec namespace 的模块名 |
| `classifier.source` | `str` | classify 函数体文本 |
| `classifier.extras` | `dict` | 分类器专用配置（api_base/api_key/model_name 等） |

#### `model_capability_map.json`

| 字段 | 类型 | 说明 |
|------|------|------|
| `vendor_map` | `list[{prefix, group, provider}]` | model_name 子串 → 品牌组/厂商映射 |
| `models` | `dict{name → {model_score, ...}}` | model_name 精确匹配 → 能力字段覆盖 |

#### `model_routing_privacy.json`

| 字段 | 类型 | 说明 |
|------|------|------|
| `patterns` | `list[{label, regex}]` | 隐私正则列表 |

## 常见问题

### 为什么开启后路由没有生效？

可能原因：

- 只配置了 1 个模型 → 路由自动跳过（"skipped (single model)"）。
- `model_routing.enabled` 没有开启。
- `model_routing.apply=false` → 路由只推荐不切，模型仍用默认。

检查日志中是否有 `[ModelRouting]` 相关输出。

### 为什么重任务总是选弱模型？

可能原因：

- `model_score` 配置不合理——弱模型 score 过高或强模型 score 过低。
- 分数表中重任务的目标分数偏低（如 `coding.hard` 只有 30）。
- 分类器误判——重任务被分类为轻任务。

检查日志中 `classifier: [...]` 行的 category、difficulty 和 score，对照 `classifier_mapper.json` 的分数表和 `model_capability_map.json` 的模型 score。

### 为什么隐私检测误判？

隐私正则可能过宽。例如 `password` 关键词正则可能匹配到"请帮我重置密码"这类正常请求。建议：

1. 先开 `privacy_check=true` 但 `apply=false`，观察日志。
2. 调整 `model_routing_privacy.json` 的正则范围。
3. 确认误判率可接受后再开 `apply=true`。

### 为什么含图请求选了非视觉模型？

可能原因：

- 没有配置 `model_type: vision` 的模型 → 全表兜底，选分数最近的。
- 图片输入格式不被识别（`_has_image` 只检查 `type=image/image_url`）。

确保 config 中有 vision 模型条目，且图片以正确的消息格式传入。

### 为什么分类器加载失败？

日志中会出现 `[ModelRouting] classifier load skipped: ...`。可能原因：

- `classifier_mapper.json` 缺少 `classifier` 字段 → fallback 到无分类器模式。
- `classifier.source` 文本有语法错误 → exec 编译失败。
- `imports` 中引用了不可用的模块。

分类器失败不影响路由——会 fallback 到 `(50, unknown, hard)`，目标分数固定 50。

### 同模型多 API 怎么独立统计？

同一个 model_name 配了多个 api_key（如 DeepSeek 3 key 预算分配），每个条目的 `model_id` 会按 `(model_name|api_base|api_key)` 派生 12 位哈希，独立统计 token 用量。也可以在 config 中显式指定 `client_id`：

```yaml
model_client_config:
  model_name: deepseek-chat
  api_base: "https://api.deepseek.com"
  api_key: "sk-aaa"
  client_id: "my-deepseek-aaa"    # ← 显式指定，不派生哈希
```

### 路由决策信息在哪里看？

路由决策写入 `ctx.extra["model_routing_decision"]`，包含推荐模型、任务分析、推理过程、OTel span 和统计快照。这个信息主要供内部 rail 链使用，不直接展示给用户。用户可通过服务端日志观察路由过程。

### `apply=false` 和 `apply=true` 的区别？

| 模式 | 行为 | 适用场景 |
|------|------|---------|
| `apply=false` | 路由只推荐模型，不切换。后续调用仍用默认模型 | 观察路由效果，调试分数/分类 |
| `apply=true` | 路由后实际切换模型（`set_llm`），后续调用用推荐模型 | 生产使用，自动按任务选模型 |
