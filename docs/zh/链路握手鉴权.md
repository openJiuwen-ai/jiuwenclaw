# 链路握手鉴权（Link-Auth）

## 1. 背景与目标

JiuwenClaw 控制面由两条 WebSocket 长连接控制链路串联：

- **Claw Manager ↔ Gateway**：Manager 向 Gateway 下发模型凭据与策略配置。
- **Gateway ↔ AgentServer**：Gateway 向运行 Agent 的 AgentServer 下发指令。

此前这两条链路缺乏身份认证：任何能够访问对应端口的进程均可接入。其核心风险在于——被攻陷的沙箱代码可能沿链路**反向接入控制面或 Agent 执行面**，造成越权。

本能力在握手阶段为两条链路引入**双向身份认证**，达成两项目标：

1. 阻断未授权进程接入控制链路（防越权接入）。
2. 确保连接双方均为合法对端，防止中间人劫持与对端冒充。

## 2. 方案概览：非对称签名 + TOFU 指纹固定

本方案采用基于 **Ed25519** 的非对称身份认证，配合首次信任（TOFU）与指纹固定机制建立信任锚。

### 2.1 身份密钥

每个端（Manager / Gateway / AgentServer）各持有一对 Ed25519 身份密钥：

- **私钥永不出端，仅用于签名**；
- **公钥可公开**，随握手令牌一并出示。

整套机制**无任何预共享秘密**。这是相较对称（共享密钥）方案的关键优势：各端独立持有自身私钥，无需在部署前于互不可达的环境间预置同一把密钥，天然适配独立部署与按需调度的场景（进程级部署与 K8s 托管均适用）。

### 2.2 握手令牌（CLT）

握手期出示的一次性身份证明，由签发者私钥签名。其载荷包含：

| 字段 | 含义 |
|---|---|
| 签发者身份 | 标识签发者是哪一端 |
| 类型 | 端的角色类型（Manager / Gateway / AgentServer） |
| 签发时间 | 用于有效期校验 |
| 随机数（nonce） | 用于防重放 |
| 签发者公钥 | 供验证方验签并比对指纹 |

### 2.3 双向认证流程

| 方向 | 出示方 | 出示位置 | 验证方 | 目的 |
|---|---|---|---|---|
| 正向 | 发起连接方（Gateway） | 握手头 `X-Claw-Link-Token` | 被连方（Manager / AgentServer） | 确认接入方为合法 Gateway，防越权接入 |
| 反向 | 被连方（Manager / AgentServer） | 首帧 `connection.ack` 内 | 发起方（Gateway） | 确认所连为合法对端，防中间人与冒充 |

每次握手双向各完成一次验签：发起方在握手头中出示自签令牌供被连方验证；被连方在握手后首帧回送自签令牌供发起方验证。

### 2.4 信任锚：TOFU 与指纹固定

验证方对对端公钥的信任通过**首次信任 + 指纹固定**建立：

- 验证方**首次**见到某身份的公钥时，记录其指纹；
- 此后每次握手，将对端出示的公钥指纹与已记录值**逐次比对**；
- **指纹不一致即拒绝**。

该机制的前提是：首次握手发生于可信状态（初始部署或纳管阶段）。一旦指纹固定，后续任何公钥替换均会被识别并拒绝。

## 3. 密钥管理与持久化

| 端 | 身份密钥来源 | 持久化 | 说明 |
|---|---|---|---|
| Manager | 复用其签名身份密钥（单例） | 落 Manager 数据库 | 私钥本机自持 |
| Gateway | 自身签名密钥对 | 落 Gateway 数据库 | 稳定不变，供对端固定指纹 |
| AgentServer | 每进程启动时临时生成 | 不落库 | 为按需拉起的临时实例 |

各端的指纹固定记录保存在进程内（内存）。

## 4. 开关与灰度上线

本能力通过环境变量控制，支持平滑灰度上线与随时回退。

### 4.1 配置项

| 变量 | 取值 / 默认 | 说明 |
|---|---|---|
| `CLAW_LINK_AUTH_MODE` | `off`（默认）/ `observe` / `enforce` | 认证模式，见下表 |
| `CLAW_LINK_TOKEN_TTL` | 整数秒，默认 `300` | 令牌有效期 |

### 4.2 三档模式

| 模式 | 行为 | 用途 |
|---|---|---|
| `off` | 不进入认证逻辑 | 默认。行为与引入本能力之前完全一致，便于平滑上线与回退 |
| `observe` | 验签并记日志，但不拒绝 | 灰度观察。用于在正式启用前确认各端密钥就绪、连接均能通过验签 |
| `enforce` | 验签不通过即拒绝 | 正式启用。无有效令牌的连接在握手阶段即被拒绝 |

### 4.3 令牌的现签机制

令牌**每次连接现签**：每次连接均携带新的 nonce 与新的签发时间，断线重连不复用旧令牌。结合短有效期，确保令牌即使泄露也难以被重用。

### 4.4 推荐上线路径

`off` →（确认各端身份密钥就绪）→ `observe`（观察日志，确认所有连接均能正常验签）→ `enforce`（正式启用）。

### 4.5 部署注意（进程级 / k8s）

三条链路的各端都需读到一致的 `CLAW_LINK_AUTH_MODE`，否则会出现"一端签、另一端不验/不签"导致握手失败（例如 AgentServer 为 `off` 时不签 `connection.ack` 反向令牌，`enforce` 的 Gateway 反向校验会失败）。

- **进程级**：各端从同一份 `.env`（`CLAW_LINK_AUTH_MODE` / `CLAW_LINK_TOKEN_TTL`）读取；由控制面 `subprocess` 拉起的 AgentServer 继承父进程环境，自动一致。
- **k8s**：Pod 不继承宿主环境。在**控制面（Manager / Gateway）Pod** 上设置 `CLAW_LINK_AUTH_MODE`（及 `CLAW_LINK_TOKEN_TTL`）后，Runtime 的部署器（k8s / docker）会**自动把这两个变量透传给它拉起的 AgentServer Pod/容器**，无需在 AgentServer 镜像里另行配置。

## 5. 安全模型与边界

### 5.1 可防护的威胁

| 威胁 | 防护手段 |
|---|---|
| 未授权进程接入控制链路 | 握手期双向验签，无有效令牌即拒 |
| 对端冒充 / 公钥替换 | 指纹固定，指纹不一致即拒 |
| 令牌重放 | nonce + 有效期（TTL）校验 |
| 令牌窃取后重用 | 令牌一次性、短有效期、每次现签 |

### 5.2 信任边界

- 信任引导依赖"**首次握手发生于可信状态**"这一前提。本能力与传输层 TLS 构成纵深防御，但**不覆盖首次握手即遭中间人劫持**的场景。
- 本能力为握手期身份认证，与传输层加密相互补充，建议在生产环境中叠加使用。

### 5.3 与其他安全能力的关系

链路握手鉴权与配置下发的**加签验签**、**字段级加解密**为相互独立、分层叠加的能力，各自作用于不同层面，互不影响、可独立启用。

## 6. 实现位置

握手鉴权的密码学能力（Ed25519 令牌签发/验证、nonce 防重放、指纹固定）由 Runtime 的基础安全模块提供，复用其 Ed25519 原语，不再单独成包：

- `openjiuwen_runtime.foundation.security.link_auth` —— 令牌 `build_token` / `build_token_header` / `verify_token` / `verify_and_pin`、`NonceCache`、进程内 TOFU 指纹固定 `InMemoryPinStore`、开关 `get_auth_mode` 等。本平台三条链路的指纹固定均用 `InMemoryPinStore`（进程内 TOFU）。
- Runtime 另提供落库显式绑定 `CertificatePinStore` + 异步 `verify_and_bind`（`openjiuwen_runtime.management.security`），用于有持久 DB、需跨重启保持绑定的场景；本平台暂未启用。

各端集成点：Manager `manager_ws_server/handshake_auth.py`、Gateway `manager_ws_client`、Gateway→AgentServer `jiuwenclaw/gateway/agent_client.py`、AgentServer `jiuwenclaw/agentserver/agent_ws_server.py`。详见 Runtime 文档《安全模块》link-auth 一节。
