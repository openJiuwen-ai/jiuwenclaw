# ClawManager 配置下发字段级加解密设计

本文档描述企业级架构中 **ClawManager 下发配置时对敏感字段进行字段级加解密** 的设计方案。目标是：在不改变现有 WebSocket 下发协议主体结构、不影响非敏感字段可读性的前提下，让 `api_key`、`kubeconfig`、密码、Token 等敏感字段以密文形式在链路上传输，客户端（Gateway）接收后再解密落库使用，从根本上消除明文传输导致的泄露风险。

> **实现锚点**：
> - Manager 下发：`packages/jiuwenclaw-ee/claw_manager/src/jiuwenclaw_manager/manager_ws_server/`（`server.py`、`protocol.py`）
> - Gateway 接收：`packages/jiuwenclaw-ee/gateway/extensions/manager_ws_client/`（`ws_client/manager_ws_client.py`、`routers/manager_ws_client_router.py`）
> - 握手分发：`build_register`（Gateway 上交加密公钥）/ `_handle_register`（Manager 落库）
> - 密钥落库：Manager `instance_enc_pubkey` 表、Gateway `gateway_enc_keypair` 表（均为**新增独立表**）

---

## 1. 背景与问题

当前 ClawManager 通过 WebSocket 长连接向各 Gateway 实例下发配置，核心链路为：

```
REST API（创建/更新模板、渠道、策略）
        │
        ▼  core/* 业务层
ManagerWsServer.push_config_op(jiuwenclaw_id, config)
        │  build_config_push → json.dumps（明文）
        ▼  WebSocket 帧
{ "type": "config.push",
  "payload": { "revision", "jiuwenclaw_id", "config": { <section>: {...} } } }
        │
        ▼  ManagerWsClient._handle_config_push
        │  json.loads → on_config_push（明文）
manager_ws_client_router → 各 section handler → 写入 Gateway 本地库
```

问题在于：**`config` 整体以明文 JSON 序列化后通过 `ws.send()` 发送**（见 `server.py` 中 `raw = json.dumps(frame, ensure_ascii=False)`）。其中包含大量敏感字段：

| Section | 敏感字段 | 风险等级 |
| --- | --- | --- |
| `model_templates` | `template.api_key` | 🔴 高（大模型 API 密钥） |
| `model_templates` | `template.parameters` | 🟠 中（可能含凭证） |
| `service_config_templates` | `template.kubeconfig` | 🔴 高（K8s 集群凭证） |
| `extension_config_templates` | `template.hook_config`、`template.custom_config` | 🟠 中（可能含密码/Token） |
| `channel_config` | `channel.config` | 🟠 中（机器人 Token、Webhook 密钥） |
| `skill_whitelist_templates` | `template.skill_source` | 🟡 低（可能含带凭证 URL） |
| 各 section | `data` | 🟠 中（开放透传字段） |

即使链路启用 `wss://`（TLS），也存在以下残余风险：链路在 Manager / Gateway 任一端落盘日志、TLS 在反向代理处卸载后内网段明文转发、运维抓包排障、配置在内存/磁盘中以明文暂存等。因此需要**应用层、字段粒度**的端到端加密，与传输层 TLS 形成纵深防御。

---

## 2. 设计目标

- **字段级而非整体加密**：只加密敏感字段，`op`、`template_id`、`revision`、`enabled` 等非敏感元数据保持明文，便于排障、审计与路由。
- **非对称 + 免预共享**：采用**信封加密**——对称 AES-256-GCM 加密数据，一次性 DEK 用 Gateway 加密公钥（X25519）包裹随帧下发。公钥握手交换、落库管理，**两端无需预共享密钥**，Manager 与 Gateway 可自由配对；非对称只解决密钥分发,数据加密仍是对称。
- **协议向后兼容**：不破坏现有 `config.push` 帧结构；密文以可识别的信封（envelope）封装，新旧客户端可平滑过渡。
- **声明式敏感字段清单**：敏感字段以「section → 字段路径」白名单集中声明，新增 section 只需登记，避免散落判断。
- **失败可控**：无 Gateway 公钥时按开关拒绝下发（fail-closed）；解密失败明确报错并通过 `config.ack` 回传，不静默落明文/落密文。
- **不做的能力**：本方案不负责传输完整性/防篡改（由 [配置下发加签验签设计](配置下发加签验签设计.md) 负责），不负责信任引导（首次公钥可信性，本版暂搁置）。

---

## 3. 总体方案

### 3.1 架构示意

```
            Manager 侧                                  Gateway 侧
┌────────────────────────────────┐         ┌────────────────────────────────┐
│ push_config_op(config)         │         │ _handle_config_push(frame)     │
│   │                            │         │   │                            │
│   ▼ 生成一次性 DEK            │  wss    │   ▼ 读 enc：epk+wrapped_dek    │
│   ├─ AES-GCM(DEK) 加密字段    │ ──────▶ │   ├─ 私钥+epk 解出 DEK         │
│   ├─ Gateway 公钥包裹 DEK     │ config. │   ├─ AES-GCM(DEK) 解字段       │
│   └─ 写入 ENC 信封 + enc 元数据│  push   │   └─ 还原明文                  │
│   ▼ build_config_push          │         │   ▼ on_config_push（明文）     │
│   ▼ json.dumps / ws.send       │ ◀────── │   ▼ 写入本地库                 │
└────────────────────────────────┘ config. └────────────────────────────────┘
                                     ack
```

加解密分别插桩在**最贴近收发边界**的两个点：

- **Manager**：`server.py::push_config_op` 在 `build_config_push` 之前，对 `config` 做敏感字段加密。
- **Gateway**：`manager_ws_client.py::_handle_config_push` 在调用 `self._on_config_push(...)` 之前，对 `config` 做敏感字段解密。

这样保证：业务层（`core/*` handler）始终面对明文、无需改造；链路上始终是密文。

### 3.2 混合加密（信封加密）与密文信封

非对称加密单次只能处理很小且性能差，**无法直接加密 `kubeconfig` 这类大字段**。因此采用业界标准的**信封加密（混合加密）**——数据本身仍用**对称 AES-256-GCM** 加密以保证效率，但那把对称密钥是**每帧随机生成的一次性数据密钥（DEK, Data Encryption Key）**，再用 Gateway 的**加密公钥**把 DEK「包」起来随帧下发。这样既享受对称加密大数据的效率，又拿到非对称「免预共享、自由配对」的好处（详见 §5）。

> 关键澄清：**数据加密仍是对称的**；非对称只用来「分发那把一次性对称密钥」，并不直接加密业务数据。我们摆脱的是「部署期预共享的固定对称密钥」，而非「对称加密」本身。

**每个敏感字段值**被加密为一个**自描述信封字符串**（用本帧 DEK 加密）：

```
ENC:v1:dek:<wrap>:<base64(AES-256-GCM(DEK, plaintext))>
```

- `ENC:v1` 版本化魔术标识；`dek` 表示「用本帧数据密钥解密」（DEK 由帧级 `enc` 携带，见 §3.3）；
- `<wrap>` 为 `str`/`obj`：字符串字段直接加密；对象字段（如 `channel.config`、`parameters`、`hook_config`）先 `json.dumps` 再加密，解密后 `json.loads` 还原；
- 密文内部自带 Nonce+Tag（每字段独立随机 Nonce）。

> 仍选「字符串前缀信封」而非对象信封：多数敏感字段本身即字符串（`api_key`、`kubeconfig`），原地替换不改变 JSON Schema 形状，对既有 `*_schemas.py` 校验零侵入。

### 3.3 帧级加密元数据（携带被包裹的 DEK）

`config.push` 的 `payload` 新增可选 `enc` 字段，记录本帧加密上下文 + **被 Gateway 公钥包裹的 DEK**，作为解密的「钥匙袋」与审计依据：

```json
{
  "type": "config.push",
  "payload": {
    "revision": "2026-06-01T10:30:45Z:gw-prod-001",
    "jiuwenclaw_id": "gw-prod-001",
    "enc": {
      "scheme": "hybrid",
      "version": "v1",
      "dek_alg": "X25519-HKDF-SHA256+AES-256-GCM",
      "gw_key_fp": "<Gateway 加密公钥指纹>",
      "epk": "<base64(临时 X25519 公钥)>",
      "wrapped_dek": "<base64(用 KEK 加密的 DEK)>",
      "fields": ["model_templates.template.api_key"]
    },
    "config": {
      "model_templates": {
        "op": "create",
        "template": {
          "template_id": "tpl-001",
          "api_key": "ENC:v1:dek:str:gAAAAAB...base64...",
          "enabled": true
        }
      }
    }
  }
}
```

DEK 的包裹用 **X25519 + HKDF**（ECIES/HPKE 风格）：Manager 生成临时 X25519 密钥对，与 Gateway 静态加密公钥做 ECDH 得共享密钥 → HKDF 派生 KEK → 用 KEK(AES-GCM) 包裹 DEK；`epk`（临时公钥）随帧下发。Gateway 用自己的私钥与 `epk` 做 ECDH 还原同一 KEK、解出 DEK。

- `enc.fields`：本帧实际被加密的字段路径，便于审计；
- `gw_key_fp`：标识用哪把 Gateway 公钥加密，便于轮换期选对私钥；
- `enc` 缺省（旧 Manager 或未加密）时，客户端按「无加密」处理，保证兼容；即使没有 `enc`，客户端仍会扫描 `ENC:` 前缀兜底识别。

## 4. 详细设计

### 4.1 敏感字段清单（Sensitive Field Registry）

集中声明，Manager 与 Gateway 共享同一份定义（建议下沉到二者都可依赖的公共模块，或各自维护一份保持同步）。以「section 名 → 字段路径列表」描述，路径支持点号嵌套与 `[]` 通配数组：

```python
# sensitive_fields.py（Manager / Gateway 各持一份，保持一致）
SENSITIVE_FIELDS: dict[str, list[str]] = {
    "model_templates":            ["template.api_key", "template.parameters"],
    "service_config_templates":   ["template.kubeconfig"],
    "extension_config_templates": ["template.hook_config", "template.custom_config"],
    "channel_config":             ["channel.config"],
    "skill_whitelist_templates":  ["template.skill_source"],
    # 通用 data 字段：默认不整体加密，避免误伤路由用元数据；
    # 如需加密由具体业务在清单中显式登记子路径
}
```

字段路径解析规则：

| 路径片段 | 含义 |
| --- | --- |
| `a.b` | 进入键 `a` 下的键 `b` |
| `a[]` | 对数组 `a` 的每个元素分别处理 |
| `a[].b` | 对数组 `a` 每个元素的键 `b` 处理 |

`config` 始终为「单 section 字典」（见 `push_config_op` 的 `len(config) != 1` 校验），因此清单按当前 section 名取出对应路径列表即可。

### 4.2 加密流程（Manager 侧）

在 `push_config_op` 内、`build_config_push` 之前：① 取该实例的 Gateway 加密公钥；② 生成一次性 DEK；③ 用 DEK 加密敏感字段；④ 用 Gateway 公钥包裹 DEK：

```python
def encrypt_sensitive_fields(section, body, dek) -> tuple[dict, list[str]]:
    """用本帧 DEK 对登记的敏感字段就地加密。"""
    paths = SENSITIVE_FIELDS.get(section, [])
    encrypted_paths, body = [], copy.deepcopy(body)
    for path in paths:
        for holder, key, value in iter_targets(body, path):
            if value is None or _already_enc(value):
                continue
            wrap = "str" if isinstance(value, str) else "obj"
            plaintext = value if wrap == "str" else json.dumps(value, ensure_ascii=False)
            cipher = aes_gcm_encrypt(dek, plaintext)          # 每字段独立随机 Nonce
            holder[key] = f"ENC:v1:dek:{wrap}:{base64encode(cipher)}"
            encrypted_paths.append(f"{section}.{path}")
    return body, encrypted_paths
```

接入点（`server.py::push_config_op`）：

```python
section, section_body = next(iter(config.items()))
gw_pub = load_gateway_enc_pubkey(jiuwenclaw_id)   # 握手时落库的 Gateway 加密公钥（§5）
if gw_pub is not None:
    dek = os.urandom(32)                                       # 一次性数据密钥
    enc_body, enc_fields = encrypt_sensitive_fields(section, section_body, dek)
    epk, wrapped_dek = wrap_dek_x25519(gw_pub, dek)            # 临时 X25519 + HKDF 包裹 DEK
    config = {section: enc_body}
    enc_meta = {"scheme": "hybrid", "version": "v1",
                "dek_alg": "X25519-HKDF-SHA256+AES-256-GCM",
                "gw_key_fp": gw_pub.fingerprint, "epk": base64(epk),
                "wrapped_dek": base64(wrapped_dek), "fields": enc_fields}
else:
    enc_meta = None
    # 严格模式（CLAWMANAGER_CONFIG_ENC_REQUIRED=true）：含敏感字段却无公钥 → 拒绝下发
    if _has_sensitive(section, section_body) and ENC_REQUIRED:
        raise ValueError("gateway enc pubkey unavailable; refuse to push plaintext secrets")

frame = build_config_push(revision=rev, jiuwenclaw_id=jiuwenclaw_id, config=config, enc=enc_meta)
```

> `build_config_push` 增加可选参数 `enc: dict | None = None`，非空时写入 `payload["enc"]`，对旧调用方兼容。

### 4.3 解密流程（Gateway 侧）

在 `_handle_config_push` 内、调用 `self._on_config_push(...)` 之前：① 用本机加密私钥 + `epk` 解出 DEK；② 用 DEK 还原各字段：

```python
config = payload.get("config") or {}
enc = payload.get("enc") if isinstance(payload.get("enc"), dict) else None
try:
    dek = None
    if enc and enc.get("scheme") == "hybrid":
        priv = load_self_enc_privkey(enc.get("gw_key_fp"))    # 本机 X25519 私钥（按指纹选）
        dek = unwrap_dek_x25519(priv, base64decode(enc["epk"]),
                                base64decode(enc["wrapped_dek"]))
    config = decrypt_sensitive_fields(config, dek)
except DecryptError as exc:
    # 解密失败：fail-closed，回 ack 失败、不落库
    ack = build_config_ack(revision=revision, success_flag=False,
                           error_message=f"decrypt failed: {exc}")
    await ws.send(json.dumps(ack, ensure_ascii=False))
    return
```

解密遍历整个 `config`，对所有 `ENC:v1:...` 信封值用 DEK 还原：

```python
def decrypt_sensitive_fields(config, dek):
    def restore(value):
        if isinstance(value, str) and value.startswith("ENC:v1:"):
            _, _, _ref, wrap, b64 = value.split(":", 4)
            if dek is None:
                raise DecryptError("ciphertext received but DEK unavailable")
            plaintext = aes_gcm_decrypt(dek, base64decode(b64))
            return json.loads(plaintext) if wrap == "obj" else plaintext
        if isinstance(value, dict):
            return {k: restore(v) for k, v in value.items()}
        if isinstance(value, list):
            return [restore(v) for v in value]
        return value
    return restore(config)
```

> 采用「全量扫描 `ENC:` 前缀」而非「只按 `enc.fields` 路径解密」，对清单不一致具鲁棒性。`enc.fields` 主要用于审计/告警比对。

### 4.4 兼容性矩阵

| Manager | Gateway | 行为 |
| --- | --- | --- |
| 新（带 enc） | 新（能解密） | ✅ 密文传输，正常解密落库 |
| 新（带 enc） | 旧（不识别 enc） | ⚠️ 字段保留 `ENC:` 密文写库 → 不可用；通过灰度（先升级 Gateway 再开 Manager 加密开关）规避 |
| 旧（明文） | 新 | ✅ 无 `ENC:` 前缀，原样透传，等价旧行为 |
| 旧（明文） | 旧 | ✅ 现状 |

灰度策略：**先全量升级 Gateway（具备解密能力但兼容明文）→ 再通过 Manager 开关 `CLAWMANAGER_CONFIG_ENC_ENABLED` 灰度开启加密**。

## 5. 密钥管理（非对称密钥对 + 握手分发）

加解密采用**非对称密钥对 + 信封加密**。与签名相反方向:数据是 Manager→Gateway 流动、Manager 加密、Gateway 解密,而**解密必须用私钥**,所以**加密密钥对归 Gateway 所有**——Gateway 持加密私钥,把自己的**加密公钥**交给 Manager,Manager 用它包裹一次性 DEK。这样两端无需预共享密钥,Manager 与 Gateway 可自由配对纳管。

### 5.1 密钥归属与算法

| 项 | 说明 |
| --- | --- |
| 数据加密 | **AES-256-GCM**(对称),密钥为每帧一次性 DEK,密文自带 Nonce+Tag。 |
| DEK 包裹 | **X25519 + HKDF-SHA256**(ECIES/HPKE 风格),`enc.dek_alg`。 |
| 私钥 | **Gateway 持有**(加密私钥),首启生成并持久化,**永不外发**。 |
| 公钥 | Gateway 的加密公钥,**握手时上交 Manager**,落 Manager 库。 |
| fingerprint | 公钥 SHA-256 指纹,写入 `enc.gw_key_fp`,Gateway 据此选对应私钥(轮换期可多对并存)。 |

> 方向对照:**验签**是 Manager 公钥→Gateway(见[加签验签设计](配置下发加签验签设计.md));**加解密**是 Gateway 公钥→Manager。一次握手交换两份公钥,方向相反、用途不同。

### 5.2 握手期公钥交换

Gateway 加密公钥在**注册握手**(`register`)时上交 Manager,复用既有握手通道:

```
Gateway ──register（带 Gateway 加密公钥 enc_pubkey + 指纹 + alg）──▶ Manager
                                                  │ 落库到 Manager 侧（§5.3）
Gateway ◀──register.ack（带 Manager 签名公钥，见加签文档）── Manager
        │ 确认配对、落库对端签名公钥
此后 Manager 下发 config.push 时用该 Gateway 公钥包裹 DEK
```

- Gateway 在 `build_register` 中附带:`enc_pubkey`(base64)、`enc_alg="X25519"`、`enc_pubkey_fp`。
- Manager `_handle_register` 收到后,把 Gateway 加密公钥写入 Manager 侧库(§5.3),与该实例信息关联。

### 5.3 落库（严格不破坏现有表）

> ⚠️ DB 框架 `init_table` 仅 `CREATE TABLE IF NOT EXISTS`、**不做列迁移**。一律**新增独立表,绝不改动 `instance_info` 等既有表**(否则存量部署既不加列,又会因模型与实表列不一致而读写报错)。

- **Manager 侧**新增表 `instance_enc_pubkey`(按 `jiuwenclaw_id` 1:1,与实例信息关联,即「公钥和 manager 信息存一起」):

  | 列 | 说明 |
  | --- | --- |
  | `jiuwenclaw_id` | 实例 id(关联 `instance_info`,但**不改它**) |
  | `enc_alg` | `X25519` |
  | `public_key` | Gateway 加密公钥(base64/PEM) |
  | `fingerprint` | 公钥 SHA-256 指纹 |
  | `status` | `bound` / `revoked` |
  | `bound_at` / `updated_at` | 时间戳 |

- **Gateway 侧**加密**密钥对**(含私钥)存于本机受保护存储:新增表 `gateway_enc_keypair`(按 `jiuwenclaw_id` 隔离,存私钥+公钥+指纹+版本),私钥所在文件/库权限收紧(0600 / KMS);**私钥绝不外发**。

### 5.4 生命周期：生成 / 分发 / 配对 / 轮换 / 销毁

| 阶段 | 动作 |
| --- | --- |
| 生成 | Gateway 首启生成 X25519 加密密钥对并持久化 |
| 分发 | 握手时把公钥上交 Manager(§5.2) |
| 配对确认 | Manager 记录公钥+指纹、与实例关联;Gateway 侧由签名公钥配对(见加签文档) |
| 轮换 | Gateway 生成新密钥对 → 重新握手上交新公钥 → Manager 切新公钥加密;过渡期 Gateway 保留新旧私钥(按 `gw_key_fp` 选),完成后删旧 |
| 销毁(解绑) | 实例被删除/解绑时(Manager `delete_instance` → `delete_instance_row`;Gateway 解绑流程)**删除对应公钥/密钥行**。**心跳超时下线 ≠ 解绑**:离线不删,重连复用 |

> 信任引导(首次收到公钥如何确保非中间人伪造)暂不在本版处理,后续可叠加 wss/TLS、指纹预共享或 TOFU + 控制台确认。

## 6. 配置开关

新增环境变量（沿用 `infrastructure/config.py` 的 `pydantic-settings` 风格）：

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `CLAWMANAGER_CONFIG_ENC_ENABLED` | `false` | Manager 是否启用字段级加密下发（灰度开关） |
| `CLAWMANAGER_CONFIG_ENC_REQUIRED` | `false` | 严格模式：含敏感字段但无 Gateway 公钥时拒绝下发（fail-closed） |
| `GATEWAY_CONFIG_DEC_ENABLED` | `true` | Gateway 是否对 `ENC:` 信封执行解密（关闭即按原文落库，仅用于排障） |

> **不再有共享加密密钥的环境变量**（如旧版的 `*_ENC_KEY`）：Gateway 加密公钥握手上交、落 Manager 库;Gateway 加密私钥本机自持。密钥来自握手分发与落库管理,而非两端预配。

## 7. 关键流程时序

```
REST API ──▶ core/* ──▶ ManagerWsServer.push_config_op(config)
                              │
                              │ 1. 取 section / body + 该实例 Gateway 加密公钥
                              │ 2. 生成一次性 DEK
                              │ 3. encrypt_sensitive_fields(DEK) + 公钥包裹 DEK → enc 元数据
                              │ 4. build_config_push(config, enc=含 epk/wrapped_dek)
                              │ 5. json.dumps → ws.send  ─────────────────┐
                                                                          ▼
                                          ManagerWsClient._handle_config_push
                                              │ 6. 读 payload.enc，私钥+epk 解出 DEK
                                              │ 7. decrypt_sensitive_fields(config, DEK)
                                              │    └─ 失败 → config.ack(success=false) ✗
                                              │ 8. on_config_push(revision, jid, 明文config)
                                              │ 9. router → section handler → 写本地库
                                              │ 10. build_config_ack(success=true)
                              ◀───────────────┘ ws.send(ack)
push_config_op 等待 ack（30s 超时，复用既有 _PendingConfigAck 机制）
```

## 8. 安全性分析

| 威胁 | 缓解 |
| --- | --- |
| 链路明文抓包获取密钥 | 敏感字段密文传输；即便 TLS 卸载/内网明文段也不暴露 |
| Manager/Gateway 日志泄露 | 日志中字段为 `ENC:` 密文；建议同时对日志做 `api_key` 等键名脱敏 |
| 清单不同步导致漏加密 | 严格模式 `ENC_REQUIRED` 兜底；解密侧全量扫描 `ENC:` 前缀 |
| 私钥泄露 | 加密私钥仅存 Gateway 本机受保护存储、**永不外发**；链路上只有公钥与被公钥包裹的一次性 DEK |
| DEK 泄露影响面 | DEK 每帧一换、随用随弃；单帧 DEK 泄露不影响其它帧 |
| 密文被篡改/重放 | **不在本方案范围**，由 [加签验签](配置下发加签验签设计.md) 覆盖，二者叠加构成完整保护 |

> 注意：字段级加密**只保证机密性，不保证完整性与防篡改**。AES-GCM 虽含 Tag 可检测单字段密文被改，但无法防止攻击者整体替换 `op`/`template_id` 等明文字段或重放旧帧。因此本方案需与加签验签方案配套启用。

## 9. 测试要点

- **单元**：`encrypt/decrypt_sensitive_fields` 对字符串字段、对象字段（`json` 往返）、数组通配路径、`None`、已加密幂等（不二次加密）的正确性。
- **DEK 包裹/解包**：X25519 包裹 DEK → 用对应私钥解出同一 DEK；错误私钥/指纹不匹配 → 解包失败 fail-closed。
- **握手分发**：register 携带 Gateway 加密公钥 → Manager 落库 `instance_enc_pubkey`；解绑后公钥行删除、再下发即拒。
- **兼容**：旧 Manager（无 enc）→ 新 Gateway 透传；新 Manager → 旧 Gateway 灰度边界。
- **失败路径**：无 Gateway 公钥时严格模式拒绝下发；DEK 解不出/解密失败回 `config.ack(success=false)` 且不落库。
- **端到端**：以 `model_templates.template.api_key` 为例，断言链路上为密文、Gateway 本地库为明文。
