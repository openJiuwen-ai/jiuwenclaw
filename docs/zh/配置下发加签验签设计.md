# ClawManager 配置下发加签验签设计

本文档描述企业级架构中 **ClawManager 下发配置时进行加签（签名）与验签（验证）** 的设计方案。目标是：为每一帧 `config.push` 附加密码学签名，Gateway 接收后先验签再应用配置，确保配置在传输过程中**未被篡改、来源可信、且不可被重放**，从而提升企业级配置分发链路的完整性与真实性保障。

> **实现锚点**：
> - Manager 下发：`packages/jiuwenclaw-ee/claw_manager/src/jiuwenclaw_manager/manager_ws_server/`（`server.py`、`protocol.py`）
> - Gateway 接收：`packages/jiuwenclaw-ee/gateway/extensions/manager_ws_client/`（`ws_client/manager_ws_client.py`、`routers/manager_ws_client_router.py`）
> - 协议帧：`config.push` / `config.ack`（见 `protocol.py::build_config_push` / `build_config_ack`）

---

## 1. 背景与问题

ClawManager 经 WebSocket 向各 Gateway 下发配置，当前帧结构为：

```json
{
  "type": "config.push",
  "payload": {
    "revision": "2026-06-01T10:30:45Z:gw-prod-001",
    "jiuwenclaw_id": "gw-prod-001",
    "config": { "model_templates": { "op": "create", "template": { ... } } }
  }
}
```

Gateway 侧 `_handle_config_push` 收到后**未做任何来源校验或完整性校验**，直接 `json.loads` 解析并交由 `on_config_push` 写入本地库（见 `manager_ws_client.py`）。这带来如下完整性风险：

| 风险 | 说明 |
| --- | --- |
| **篡改（Tampering）** | 中间人或被入侵的代理节点修改 `config` 内容（如把 `api_base` 改成钓鱼地址、`op` 由 `deactivate` 改为 `activate`），Gateway 无从察觉。 |
| **伪造（Spoofing）** | 任何能连上 Gateway/Manager 端口或伪装 WS 服务端的实体均可下发任意配置。 |
| **重放（Replay）** | 攻击者截获一帧旧配置并重新发送，使 Gateway 回退到历史（可能含已吊销凭证）的配置。 |
| **乱序覆盖** | 旧 `revision` 帧晚到覆盖新配置。 |

即便启用 `wss://`（TLS）解决了「外部网络」的窃听与篡改，仍无法覆盖：TLS 在反向代理/网关处卸载后的内网段、被攻陷的中间服务、以及**应用层重放**。因此需要**应用层、端到端**的加签验签，与 TLS 形成纵深防御，并为配置分发提供可审计的真实性凭证。

---

## 2. 设计目标

- **完整性 + 真实性**：每帧 `config.push` 携带覆盖关键字段的签名，Gateway 验签通过才应用，确保「内容未改 + 来自可信 Manager」。
- **防重放**：引入 `nonce` + `timestamp` 时间窗 + `revision` 单调性校验，拒绝重放与陈旧帧。
- **非对称 + 免预共享**：采用非对称签名 **Ed25519**（Manager 持私钥签名、Gateway 持公钥验签，私钥不下放）。公钥在握手时交换、落库管理，**两端无需预共享密钥**，Manager 与 Gateway 可自由配对纳管；算法经 `SignatureProvider` 接口可插拔。
- **协议向后兼容**：签名以可选 `sig` 块附加在 `payload` 上，不破坏既有帧；支持灰度。
- **双向可选**：`config.ack` 亦可签名，使 Manager 能验证回执真实性（可选增强）。
- **失败 fail-closed**：验签失败 / 时间窗超限 / nonce 重复 → 拒绝应用并回 `config.ack(success=false)`，不静默放行。
- **与加密解耦又可叠加**：与 [字段级加解密](配置下发字段级加解密设计.md) 互不依赖，但建议「先加密后签名」叠加启用（见 §8）。

## 3. 总体方案

### 3.1 架构示意

```
            Manager 侧                                  Gateway 侧
┌────────────────────────────────┐         ┌────────────────────────────────┐
│ push_config_op(config)         │         │ _handle_config_push(frame)     │
│   ▼ build_config_push          │         │   ▼ 取 payload + sig           │
│   ▼ sign_frame(payload)        │  wss    │   ▼ verify_frame(payload, sig) │
│   ├─ 规范化序列化(canonical)   │ ──────▶ │   ├─ 规范化序列化(canonical)   │
│   ├─ 拼 nonce/ts/key_id        │ config. │   ├─ 校验 ts 时间窗            │
│   ├─ SignatureProvider.sign    │  push   │   ├─ 校验 nonce 未用过         │
│   └─ 写入 payload.sig          │         │   ├─ 校验 revision 单调       │
│   ▼ json.dumps / ws.send       │         │   ├─ SignatureProvider.verify │
│                                │         │   └─ 任一不过 → ack(false) ✗  │
│                                │ ◀────── │   ▼ on_config_push（已验证）   │
└────────────────────────────────┘ config. └────────────────────────────────┘
                                     ack
```

验签插桩在 **`_handle_config_push` 最前端**（解析 payload 之后、调用 `on_config_push` 之前），确保**未经验证的配置永远不进入业务层**。

### 3.2 签名块（Signature Envelope）

在 `config.push` 的 `payload` 中新增可选 `sig` 字段：

```json
{
  "type": "config.push",
  "payload": {
    "revision": "2026-06-01T10:30:45Z:gw-prod-001",
    "jiuwenclaw_id": "gw-prod-001",
    "config": { "model_templates": { "op": "create", "template": { ... } } },
    "sig": {
      "alg": "Ed25519",
      "key_id": "v1",
      "ts": "2026-06-01T10:30:45.123Z",
      "nonce": "b1c2d3e4f5a6...",
      "value": "base64(signature)"
    }
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `alg` | 签名算法：`Ed25519`（默认非对称） |
| `key_id` | 签名公钥版本（`key_version`），验签侧据此从库中选对应 Manager 公钥，支持多版本/轮换 |
| `ts` | 签名时间戳（UTC，毫秒精度），用于时间窗防重放 |
| `nonce` | 随机数（≥128bit，hex/base64），用于 nonce 去重防重放 |
| `value` | 签名值 = `Sign(canonical_bytes)` 的 base64 |

### 3.3 签名覆盖范围与规范化（Canonicalization）

签名必须覆盖**所有需保护的关键内容**，且签名/验签两侧对「被签字节」的构造必须**逐字节一致**。定义待签内容为：

```
signing_string = canonical_json({
    "revision":      payload.revision,
    "jiuwenclaw_id": payload.jiuwenclaw_id,
    "config":        payload.config,
    "alg":           sig.alg,
    "key_id":        sig.key_id,
    "ts":            sig.ts,
    "nonce":         sig.nonce
})
signature = Sign(signing_string.encode("utf-8"))
```

其中 `canonical_json` 为**确定性 JSON 序列化**，规则：

- 键按字典序排序（`sort_keys=True`）；
- 无多余空白（`separators=(",", ":")`）；
- `ensure_ascii=False`，UTF-8 编码（与现有 `json.dumps(..., ensure_ascii=False)` 一致）；
- 不含 `sig.value` 自身（避免自指）。

> 关键点：**`config` 同时参与签名**，因此任何对配置内容的篡改都会使验签失败；`ts`/`nonce`/`key_id`/`alg` 也纳入签名，防止攻击者改动这些元数据绕过防重放。采用规范化序列化而非「直接对收到的原始字节验签」，是为了不依赖中间环节是否保持字节不变（如重新序列化、键序变化），同时也兼容与字段级加密叠加时 `config` 内含密文信封的情况（密文字符串照常入签）。

## 4. 详细设计

### 4.1 签名流程（Manager 侧）

`protocol.py` 增加签名构造能力，`server.py::push_config_op` 在 `build_config_push` 之后、`json.dumps` 之前签名：

```python
# protocol.py
def build_config_push(*, revision, jiuwenclaw_id, config, enc=None) -> dict:
    payload = {"revision": revision, "jiuwenclaw_id": jiuwenclaw_id, "config": config}
    if enc:
        payload["enc"] = enc
    return {"type": FRAME_TYPE_CONFIG_PUSH, "payload": payload}

def attach_signature(frame: dict, signer: SignatureProvider, key_id: str) -> dict:
    payload = frame["payload"]
    ts = utc_now_iso_ms()
    nonce = secrets_token_hex(16)
    signing = canonical_json({
        "revision": payload["revision"], "jiuwenclaw_id": payload["jiuwenclaw_id"],
        "config": payload["config"], "alg": signer.alg, "key_id": key_id,
        "ts": ts, "nonce": nonce,
    })
    payload["sig"] = {
        "alg": signer.alg, "key_id": key_id, "ts": ts, "nonce": nonce,
        "value": base64(signer.sign(signing.encode("utf-8"))),
    }
    return frame
```

接入点（`server.py::push_config_op`）：

```python
frame = build_config_push(revision=rev, jiuwenclaw_id=jiuwenclaw_id, config=config, enc=enc_meta)
signer = get_signature_provider()          # 加载 Manager Ed25519 私钥（manager_identity），见 §5
if signer is not None:
    frame = attach_signature(frame, signer, key_id=signer.key_version)  # key_id 即公钥版本
elif SIGN_REQUIRED:
    raise ValueError("signature provider unavailable; refuse to push unsigned config")
raw = json.dumps(frame, ensure_ascii=False)
async with client.send_lock:
    await client.ws.send(raw)
```

> 注意 `ts`/`nonce` 在每次 `push_config_op` 调用时新生成。对 `push_config_op_to_all` 的逐实例下发，每个实例帧拥有独立 `revision`、`ts`、`nonce`，签名各自独立。

### 4.2 验签流程（Gateway 侧）

`_handle_config_push` 在解析出 `payload` 后、调用 `self._on_config_push(...)` 之前插入完整校验链：

```python
async def _handle_config_push(self, ws, data):
    payload = data.get("payload")
    revision = str(payload.get("revision") or "")
    jiuwenclaw_id = payload.get("jiuwenclaw_id")
    config = payload.get("config") or {}
    sig = payload.get("sig") if isinstance(payload.get("sig"), dict) else None

    verifier = get_signature_provider()   # 按 sig.key_id（版本）从 manager_sign_pubkey 取 Manager 公钥
    if verifier is not None or SIGN_REQUIRED:
        ok, err = verify_frame(payload, sig, verifier)
        if not ok:
            ack = build_config_ack(revision=revision, success_flag=False,
                                   error_message=f"signature verify failed: {err}")
            await ws.send(json.dumps(ack, ensure_ascii=False))
            logger.warning("[ManagerWsClient] reject config.push: %s", err)
            return
    # 验签通过 → 进入既有业务流程
    ...
```

`verify_frame` 校验链（**任一不过即拒绝，顺序从廉价到昂贵**）：

```python
def verify_frame(payload, sig, verifier) -> tuple[bool, str | None]:
    if sig is None:
        return (False, "missing signature") if SIGN_REQUIRED else (True, None)
    # 1. 算法/密钥白名单
    if sig["alg"] not in ALLOWED_ALGS:           return False, "alg not allowed"
    # 2. 时间窗（默认 ±300s，容忍时钟漂移）
    if abs(now() - parse(sig["ts"])) > SKEW:     return False, "timestamp out of window"
    # 3. nonce 去重（带 TTL 的已见集合，TTL ≥ 时间窗）
    if nonce_seen(sig["nonce"]):                 return False, "nonce replayed"
    # 4. revision 单调（不接受 <= 已应用 revision 的帧）
    if not revision_newer(payload["revision"]):  return False, "stale revision"
    # 5. 密码学验签（最后做，最贵）
    signing = canonical_json({...同 §3.3...})
    if not verifier.verify(signing.encode(), base64decode(sig["value"]), key_id=sig["key_id"]):
        return False, "bad signature"
    nonce_remember(sig["nonce"]);  revision_commit(payload["revision"])
    return True, None
```

> `nonce_remember` / `revision_commit` 仅在**全部校验通过后**执行，避免被构造的无效帧污染去重集合。

### 4.3 防重放设计

三重防线叠加：

| 机制 | 作用 | 实现 |
| --- | --- | --- |
| **时间窗** | 拒绝过旧/未来帧 | `|now - ts| ≤ 300s`（可配），依赖 NTP 同步 |
| **nonce 去重** | 拒绝窗内重复帧 | 内存 `{nonce: expire_at}`，TTL = 时间窗 + 余量；定期清理 |
| **revision 单调** | 拒绝旧配置回放/乱序 | 记录每实例「最后成功应用的 revision」，新帧须更大（`revision` 为 ISO 时间戳，天然可比较） |

nonce 集合仅需覆盖「时间窗」时长，故内存占用有界；Gateway 重启后时间窗内的极少量重放由 `revision` 单调性兜底。

### 4.4 兼容性矩阵

| Manager | Gateway | 行为 |
| --- | --- | --- |
| 新（带 sig） | 新（验签） | ✅ 签名校验通过后应用 |
| 新（带 sig） | 旧（忽略 sig） | ✅ 旧 Gateway 忽略未知字段，等价旧行为（弱化保护，灰度过渡态） |
| 旧（无 sig） | 新（`SIGN_REQUIRED=false`） | ✅ 兼容明文帧，记录告警 |
| 旧（无 sig） | 新（`SIGN_REQUIRED=true`） | ✗ 拒绝并告警（强制安全态） |
| 任意 | 验签失败 | ✗ `config.ack(success=false)`，不落库 |

灰度策略：**先升级 Manager 开启签名（Gateway 旧版忽略）→ 升级全部 Gateway 具备验签能力 → 最后将 Gateway 切到 `SIGN_REQUIRED=true` 强制**。

## 5. 密钥与算法管理（非对称 + 握手分发）

签名采用**非对称算法 Ed25519**：Manager 持**签名私钥**对配置签名，Gateway 持 Manager 的**签名公钥**验签。私钥永不离开 Manager；公钥不是秘密，握手时下发即可。相比对称 HMAC，**两端无需预共享密钥**——这正是关键：对称密钥只能部署期注入、强制两端一致才能配对，而公钥可在握手时自由交换，因此 **Manager 与 Gateway 可自由关联纳管**。

### 5.1 密钥归属与算法

| 项 | 说明 |
| --- | --- |
| 算法 | **Ed25519**（签名/验签），`sig.alg = "Ed25519"`。短、快、实现简单。 |
| 私钥 | **Manager 持有**，首次启动生成并持久化，**永不下发、不入任何下发链路**。 |
| 公钥 | Manager 的签名公钥，**握手时下发给 Gateway**，落 Gateway 库。 |
| key_version | 公钥版本号，写入 `sig.key_id`；支持多版本并存，为滚动轮换提供基础。 |
| fingerprint | 公钥 SHA-256 指纹，用于 Gateway「确认配对」与轮换比对。 |

`SignatureProvider` 接口（实现可插拔，默认 Ed25519）：

```python
@runtime_checkable
class SignatureProvider(Protocol):
    alg: str
    def sign(self, data: bytes) -> bytes: ...
    def verify(self, data: bytes, signature: bytes) -> bool: ...
```

### 5.2 握手期公钥交换

公钥在 Gateway ↔ Manager 的**注册握手**（`register` / `register.ack`）时交换，复用既有握手通道，**不引入额外交互**：

```
Gateway ──register（带 Gateway 加密公钥，详见加解密文档）──▶ Manager
Gateway ◀──register.ack（带 Manager 签名公钥 + key_version + 指纹）── Manager
        │
        ▼ 校验/记录指纹 = “确认配对”，写入本地库
此后所有 config.push 用该公钥验签
```

- Manager 在 `build_register_ack` 中附带：`sign_pubkey`(base64)、`sign_alg="Ed25519"`、`key_version`、`sign_pubkey_fp`。
- Gateway 收到后：比对/记录指纹（领导所说的「Gateway 确认自己已配对」），把公钥写入本地库，标记 `status=bound`。

> 同一次握手里，Gateway 还会把**自己的加密公钥**上交 Manager（见 [配置下发字段级加解密设计](配置下发字段级加解密设计.md)）。即**一次握手交换两份公钥，方向相反**：Manager 签名公钥 → Gateway（验签用）；Gateway 加密公钥 → Manager（加密用）。

### 5.3 落库（严格不破坏现有表）

> ⚠️ 当前 DB 框架的 `init_table` 仅 `CREATE TABLE IF NOT EXISTS`、**不做列迁移**。因此**一律新增独立表，绝不改动 `instance_info` 等既有表**（否则存量部署既不会自动加列，又会因模型与实表列不一致而读写报错）。

- **Gateway 侧**新增表 `manager_sign_pubkey`（落在 Gateway 企业配置库、按 `jiuwenclaw_id` 实例隔离，即「公钥和 Manager 信息存在一起」）：

  | 列 | 说明 |
  | --- | --- |
  | `jiuwenclaw_id` | 实例 id（关联本实例与对端 Manager） |
  | `manager_id` | 对端 Manager 标识 |
  | `sign_alg` | `Ed25519` |
  | `public_key` | Manager 签名公钥（base64/PEM） |
  | `key_version` | 公钥版本 |
  | `fingerprint` | 公钥 SHA-256 指纹 |
  | `status` | `bound` / `revoked` |
  | `bound_at` / `updated_at` | 时间戳 |

- **Manager 侧**签名私钥为单例，持久化于**受保护存储**：新增单行表 `manager_identity`（或配置目录下权限 0600 的密钥文件 / KMS）保存 Ed25519 私钥与当前 `key_version`；**私钥绝不入下发链路**。

### 5.4 生命周期：生成 / 分发 / 配对 / 轮换 / 销毁

| 阶段 | 动作 |
| --- | --- |
| 生成 | Manager 首启生成 Ed25519 签名密钥对并持久化 |
| 分发 | 握手时下发公钥（§5.2） |
| 配对确认 | Gateway 比对指纹后标记 `status=bound` |
| 轮换 | Manager 生成新版本 → 用新 `key_version` 签名 → 过渡期 Gateway 同时信任新旧版本 → 删除旧版本公钥行下线 |
| 销毁（解绑） | 实例被删除/解绑时（Manager `delete_instance` → `delete_instance_row`；Gateway 解绑流程）**删除对应公钥行**。**心跳超时下线 ≠ 解绑**：`mark_instance_offline` 不删密钥，离线重连复用 |

> 信任引导（首次收到公钥如何确保不是中间人伪造）暂不在本版处理，后续可叠加 wss/TLS、指纹预共享或 TOFU + 控制台确认。

## 6. 配置开关

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `CLAWMANAGER_CONFIG_SIGN_ENABLED` | `false` | Manager 是否对 `config.push` 加签 |
| `CLAWMANAGER_CONFIG_SIGN_ALG` | `Ed25519` | 签名算法 |
| `GATEWAY_CONFIG_VERIFY_ENABLED` | `true` | Gateway 是否验签 |
| `GATEWAY_CONFIG_VERIFY_REQUIRED` | `false` | 强制态：无签名/验签失败一律拒绝（fail-closed） |
| `GATEWAY_CONFIG_SIGN_SKEW_SECONDS` | `300` | 允许的时间窗（秒） |

> **不再有共享签名密钥的环境变量**（如旧版的 `*_SIGN_KEY`）：签名公钥由握手分发、落库管理，私钥由 Manager 自持。这正是「免预共享、自由配对」的来源。

## 7. 关键流程时序

```
REST API ──▶ core/* ──▶ ManagerWsServer.push_config_op(config)
                              │ 1. build_config_push(payload)
                              │ 2. get_signature_provider()
                              │ 3. attach_signature：gen ts+nonce → canonical_json → sign
                              │ 4. json.dumps(frame) → ws.send ──────────────┐
                                                                             ▼
                                          ManagerWsClient._handle_config_push
                                              │ 5. 取 payload + sig
                                              │ 6. verify_frame：
                                              │    ① alg 白名单 ② ts 时间窗
                                              │    ③ nonce 去重 ④ revision 单调
                                              │    ⑤ canonical_json → verify
                                              │    └─ 任一不过 → config.ack(false) ✗
                                              │ 7. on_config_push(明文/已验证 config)
                                              │ 8. router → handler → 写本地库
                                              │ 9. build_config_ack(success=true)
                              ◀───────────────┘ ws.send(ack)
push_config_op 等待 ack（复用既有 _PendingConfigAck，30s 超时）
```

## 8. 与字段级加解密的叠加

两方案正交且互补，建议生产环境同时启用，遵循 **「先加密后签名（Encrypt-then-Sign）」** 顺序：

```
Manager:  明文 config ──加密敏感字段──▶ 含密文 config ──对整帧签名──▶ config.push
Gateway:  config.push ──验签(整帧)──▶ 通过 ──解密敏感字段──▶ 明文 config ──落库
```

- 签名覆盖的是「已含密文的 config」，因此**签名同时保护密文与明文字段的完整性**；
- 验签先行可在解密前就拒绝被篡改/重放的帧，避免无谓解密开销；
- 二者通过各自独立开关控制，可单独或组合灰度。

| 能力 | 字段级加密 | 加签验签 |
| --- | --- | --- |
| 机密性（防窃听） | ✅ | ❌ |
| 完整性（防篡改） | 部分（仅密文字段，GCM Tag） | ✅（全帧） |
| 真实性（防伪造） | ❌ | ✅ |
| 防重放 | ❌ | ✅ |

## 9. 安全性分析

| 威胁 | 缓解 |
| --- | --- |
| 内容篡改 | `config` 纳入签名，任何改动致验签失败 |
| 来源伪造 | Ed25519 非对称：无 Manager 私钥无法伪造签名；Gateway 只持公钥，泄露也不致伪造 |
| 重放攻击 | 时间窗 + nonce 去重 + revision 单调三重防护 |
| 元数据绕过 | `ts`/`nonce`/`alg`/`key_id` 均入签，不可单独篡改 |
| 降级攻击（剥离 sig） | `VERIFY_REQUIRED=true` 下无 sig 即拒绝 |
| 时钟漂移误杀 | 依赖 NTP；时间窗可配；窗外由 revision 兜底正确性 |
| 私钥泄露 | 私钥仅存于 Manager 受保护存储（不入下发链路）；支持按 `key_version` 轮换、解绑即销毁公钥 |

## 10. 测试要点

- **单元**：`canonical_json` 确定性（键序、空白、Unicode）；`sign/verify` 正反例；篡改 `config` 任一字节 → 验签失败。
- **防重放**：重复 nonce 拒绝；超时间窗拒绝；旧 `revision` 拒绝；重启后旧帧由 revision 兜底。
- **算法**：Ed25519 签名/验签正反例；错误 `key_id`（版本）取不到公钥拒绝；未知 `alg` 拒绝。
- **握手分发**：register.ack 携带公钥 → Gateway 落库 `manager_sign_pubkey`、指纹比对配对；解绑后公钥行删除、再下发即拒。
- **兼容/强制**：旧 Manager→新 Gateway 在 `REQUIRED=false/true` 下的放行/拒绝；无 sig 降级被拒。
- **端到端**：正常下发应用成功并 `config.ack(success=true)`；中间篡改/重放被拒并回 `success=false` 且不落库。
- **叠加**：与字段级加密同开，验证「先验签后解密」顺序与互不干扰。
