# 按需检索：改进方案审查

> 本文档整理按需检索（on-demand tool retrieval）当前实现的问题诊断、已完成的修复、待做的改造方案，以及与 ratel-ai/ratel 的对比。作为改进路线讨论与审查的基础。

---

## 一、现状回顾

### 1.1 我们的设计

按需检索是 JiuWenSwarm 面向"注册工具数量较多"场景的工具发现与调用机制。核心三件事：

- **工具发现**：每轮对话只向模型暴露少量基座工具 + 一个 `search_tools` 检索入口，其余专业工具收进隐藏清单。
- **直接调用**：搜到的工具**不写进 `tools[]`**，模型直接按工具名发起 tool call，由 `ability_manager` 按名解析执行。`tools[]` 全程恒定，保 prefix cache / kv-cache。
- **prompt 地图**：系统提示里注入"工具导航 + 隐藏工具摘要 + 使用规则"三段，告诉模型"有什么可搜"。

实现文件：

| 文件 | 职责 |
|---|---|
| `jiuwenswarm/common/tool_retrieval/search.py` | dense 检索算法核（cosine + boost） |
| `jiuwenswarm/common/tool_retrieval/embedder.py` | fastembed 模型加载 |
| `jiuwenswarm/common/tool_retrieval/summary.py` | haystack 构建 / 工具摘要 |
| `jiuwenswarm/common/tool_retrieval/corpus.py` | ghost 过滤 |
| `jiuwenswarm/agents/harness/common/rails/search_tool_rail.py` | rail：注入 + corpus 构建 + 搜索入口 |
| `jiuwenswarm/agents/harness/common/tools/search_tool.py` | `search_tools` 工具实现 |

### 1.2 检索算法（当前）

- **默认**：dense embedding（`BAAI/bge-small-zh-v1.5` via fastembed）+ 手工 boost
- **boost 策略**（`search.py:92-107`）：
  - `query == 工具名` → +1.0
  - 工具名是 query 子串 → +0.8
  - 前缀匹配 → +0.3
  - name token overlap → +0.5 / +0.25×ratio
  - `verb_intent_boost`：中英动词映射（create→创建 等）→ +0.5
- **阈值**：`min_sim=0.35`（`config.yaml`），低于此值的工具不返回
- **无 BM25**：文档（`按需检索-工具发现与直接调用.md:264`）提到"后续会引入 BM25 混合检索改善"，尚未实现

### 1.3 失败模式

`embedder.py:11` 的 `ensure_embedding_model` 加载失败时**静默返回 None**：

```python
def ensure_embedding_model(model_name="BAAI/bge-small-zh-v1.5"):
    try:
        from fastembed import TextEmbedding
        return TextEmbedding(model_name)
    except Exception:
        return None   # 静默失败
```

`search_tool_rail.py` 的 `_search_tools` 在 `_embedding_model is None` 时直接 `return []`——**搜索完全瘫痪**（只有坑 2 的纯工具名查询能救，见 §3.2）。

## 二、问题案例：`send_file_to_user` 4 次搜索失败

### 2.1 现象

用户报告：模型 4 次调用 `search_tools` 都搜不到 `send_file_to_user`：

| 次数 | query | 返回 |
|---|---|---|
| 1 | 发送文件给用户 send file | write_file、read_file、edit_file |
| 2 | send_file_to_user 发送文件下载 | write_file、read_file、list_files |
| 3 | 用户交互 询问用户 投递文件 | ask_user 等 |
| 4 | send_file_to_user | write_file |

但系统提示词里明明列出了这个工具（导航"用户交互（1 个）：...send_file_to_user" + 「文件发送」章节完整描述）。**导航能列出，search 搜不到——两者脱节。**

### 2.2 日志确认

`full.log` 里 8/3 10:09-10:10 的搜索行印证：

```
10:09:59 query='发送文件给用户 send file' top_k=3 found=3
10:10:03 query='send_file_to_user 发送文件下载' top_k=3 found=3
10:10:08 query='用户交互 询问用户 投递文件' top_k=3 found=3
10:10:11 query='send_file_to_user' top_k=1 found=1   ← 纯工具名都没命中 send_file_to_user
```

第 4 次 query 直接是工具名，`found=1` 但返回的是 `write_file`（不是 `send_file_to_user`）——说明 `send_file_to_user` 当时**根本不在搜索语料**（`_search_corpus`）里。

### 2.3 工具特性

`send_file_to_user` 是**运行时动态注册**的工具（`interface_deep.py:5170` `_update_session_tools`），每次请求根据 channel 的 `send_file_allowed` 决定是否注册：

```python
Runner.resource_mgr.add_tool(sf_tool)              # 实例
self._instance.ability_manager.add(sf_tool.card)   # card
```

注册时机敏感，是 ghost 误杀的高发地带。`按需检索-待办.md:52` 记录过历史上它被 ghost 过滤误杀的 bug（已修 resolver fallback，但 sig 缓存路径未覆盖）。

## 三、根因诊断

四个问题，分两层：

### 3.1 坑 1：sig 缓存锁死（已修复）

**位置**：`search_tool_rail.py:542` `_build_executable_corpus`

**原逻辑**：
```python
sig = frozenset(name for t in self._cached_all_tool_infos)
if sig == self._executable_sig and self._search_corpus:
    return   # 名字集合没变就跳过重新过滤
```

**问题**：
- 某轮 `send_file_to_user` 因注册时序被 ghost 过滤误杀 → `_search_corpus` 不含它
- 下一轮它注册正常了，`_cached_all_tool_infos` 名字集合**没变**（还是含它）→ `sig == _executable_sig` 命中缓存 → **跳过重新过滤** → `_search_corpus` 永远不含它
- 导航直接读 `_cached_all_tool_infos`（不过滤）→ 能列出；search 读 `_search_corpus`（过滤后）→ 搜不到。**锁死。**

### 3.2 坑 2：工具名查询无兜底（已修复）

**位置**：`search_tool_rail.py:471` `_search_tools`

query 直接是工具名（如 `send_file_to_user`）时，理应稳赢（`ql == nl` boost +1.0）。但如果工具不在 `_search_corpus`，boost 加不上；`_force_refresh_and_retry` 的"数量相等就放弃"守卫（`rail.py:498`）又让它不重试。**工具名查询无兜底。**

### 3.3 坑 3：haystack 噪音大（待修复）

**位置**：`search.py:43` `haystack_for` + `summary.py:61` `parameters_to_text`

当前 haystack：
```
memory_search 在持久化记忆中搜索。 fields: query, limit {'type': 'object', 'properties': {'query': {'type': 'string', 'description': '搜索词'}, ...}, 'required': ['query']}
```

三个毛病：
1. **名字不拆**：`memory_search` 整词，dense 模型不认识复合词
2. **JSON 结构噪音**：`type`/`properties`/`required`/`default` 高频无信息词，稀释语义
3. **enum 不突出**：cron 工具的 `enum:["status","list","add",...]` 淹没在 raw dict 里

这是 dense 检索质量差的根因之一，也是"创建定时任务"会错排到 `cron_list_jobs` 的根因。

### 3.4 embedding 失败瘫痪（待修复）

`_embedding_model is None` 时 `_search_tools` 直接 `return []`。fastembed 没装 / 模型下载失败 / 网络不通 → **搜索完全罢工**（仅坑 2 纯工具名查询能救）。

## 四、已完成的修复

### 4.1 坑 1 修复：去掉 sig 缓存

`search_tool_rail.py:542` `_build_executable_corpus`，去掉 early return，每次 `before_invoke` 都重新跑 ghost 过滤。

```python
# 修复前：sig 缓存命中就跳过
if sig == self._executable_sig and self._search_corpus:
    return

# 修复后：每次都重新过滤（运行时工具注册状态会变，缓存会把误杀锁死）
self._executable_sig = frozenset(...)
# 直接跑 filter_executable，不 early return
```

embed 缓存（`_cached_tool_sig` 在 `_precompute_tool_embeddings`）独立，不受影响——corpus 名字集合真没变时 embed 仍 short-circuit。

### 4.2 坑 2 修复：工具名 fast-path

`search_tool_rail.py:471` `_search_tools` 开头加 name fast-path，新增 `_lookup_tool_by_name` 方法：

```python
async def _search_tools(self, query, limit=10, detail_level=1):
    ...
    # query 看起来是工具名时，直接从全量清单按名查，绕过 corpus/embedding/min_sim
    name_hits = self._lookup_tool_by_name(query, detail_level=detail_level)
    if name_hits:
        return name_hits[:limit]
    ...  # 原有 dense 路径
```

触发条件：`"_" in ql and ql.replace("_","").isalnum()`（含下划线且去下划线后是字母数字）。从 `_cached_all_tool_infos`（导航读的那个全量清单）按名查，绕过 `_search_corpus` 缺失、embedding 缓存、min_sim 全套。

### 4.3 测试

`tests/unit_tests/common/test_search_tool_rail.py` 新增 3 个测试：

- `test_search_tools_name_fast_path_recovers_tool_missing_from_corpus` — `_search_corpus` 不含、`_cached_all_tool_infos` 含，query=工具名，验证返回该工具
- `test_search_tools_name_fast_path_ignores_non_name_query` — 语义查询不走 fast-path
- `test_build_executable_corpus_refilters_when_sig_unchanged` — sig 不变也重新调 `filter_executable`、`_search_corpus` 重新赋值

6 个测试全过（3 原有 + 3 新增），无破坏。

### 4.4 现场验证

8/3 11:21（修复后）：`query='send file to user'` `found=1` → 10 秒后 `[SendFileToolkit] send_file 开始 ... 有效文件=1 缺失=0`，搜索→调用链路成功。`send_file_to_user` 从"搜不到"变成"搜得到"，坑 1 生效。

## 五、待做的改造方案

### 5.1 坑 3：haystack 干净化（最高优先级）

**借鉴**：ratel `indexing.rs::searchable_text`

**改造** `haystack_for`（`search.py:43`）：

```python
def haystack_for(tool, desc_cap):
    tokens = []
    name = str(getattr(tool, "name", "") or "")
    if name:
        tokens.append(name)
        split = _split_identifier(name)   # snake_case/camelCase 拆分
        if split != name:
            tokens.append(split)
    desc = str(getattr(tool, "description", "") or "")
    if desc:
        tokens.append(desc[:desc_cap])
    _flatten(getattr(tool, "parameters", None), tokens)  # 递归抽字段名+描述+enum
    return " ".join(tokens)
```

要点：
1. **删掉** `parameters_to_text` 的 raw dict 拼接（不再把整段 JSON 塞 haystack）
2. 标识符拆分：`read_file` → `read file`，`sendEmail` → `send Email`
3. schema 只取：字段名（拆分）+ 字段 description + enum 值
4. **显式排除** JSON 结构关键字（type/properties/required/default）
5. 加测试守"haystack 不含 `type`/`properties` 字面量"

**不动** `build_tool_summary`（返回给 LLM 的完整 JSON Schema，`detail_level=3`）——那是给模型构造参数用的，必须完整；只改检索用的 haystack。

### 5.2 BM25 + hybrid + 降级

#### 5.2.1 三种检索方法

```yaml
react:
  tool_retrieval:
    method: hybrid   # bm25 | semantic | hybrid（默认 hybrid）
```

| method | 行为 | 场景 |
|---|---|---|
| `bm25` | 纯 BM25，无模型 | 离线/资源紧/工具少 |
| `semantic` | 纯 dense（现状） | 模型就绪 + 中文语义强 |
| `hybrid` | BM25 + dense RRF 融合 | 默认，质量最高 |

#### 5.2.2 降级链（解决瘫痪）

```
method=hybrid + embedding 就绪  → BM25 + dense RRF
method=hybrid + embedding 失败  → 纯 BM25（降级，不瘫痪）
method=semantic + embedding 失败 → 纯 BM25（降级，不瘫痪）  ← 不再 return []
```

最后一条是重点：即使配 `semantic`，embedding 失败也降级 BM25，不再彻底罢工。

#### 5.2.3 RRF 融合（Reciprocal Rank Fusion）

```
RRF_score(tool) = 1/(60 + rank_bm25) + 1/(60 + rank_dense)
```

只用排名，不用分数——尺度无关（BM25 分数和 cosine 不可比，直接加权会乱）。ratel `fusion.rs` 用的就是这个。

#### 5.2.4 为什么 hybrid 在我们这里特别值

| 场景 | dense | BM25 | hybrid 收益 |
|---|---|---|---|
| 英文工具名（send_file_to_user） | 整词不拆，弱 | 字面+IDF，强 | BM25 救场 |
| 中文语义（"搜索记忆"≈memory） | 跨语言，强 | 不懂同义，弱 | dense 救场 |
| enum 值（create/list/delete） | 混在 JSON 噪音 | 精确词命中 | BM25 救场 |
| embedding 失败 | 瘫痪 | 不受影响 | BM25 兜底 |

#### 5.2.5 实现路径（4 步）

1. **BM25 模块**：`common/tool_retrieval/bm25_search.py`，自己实现 BM25Okapi（公式几十行，零新依赖），参数 k1=0.9, b=0.4（ratel 调过的短文本值）
2. **haystack 复用**：坑 3 完成后，BM25 和 dense 用同一个干净 haystack
3. **RRF 融合 + 降级逻辑**：`search.py` 加 `hybrid_search`，`search_tool_rail.py` 的 `_dense_search` 改 `_search` 按 method 分发
4. **BM25 索引缓存**：`_cached_bm25_index` + sig 缓存（这次 sig 缓存安全——纯文本索引，无 ghost 探针）

#### 5.2.6 中文分词取舍

BM25 在英文 `split()` 够用，中文不行。三个选项：

1. **不专门处理中文**（推荐起步）：BM25 管英文（工具名+enum+字段名），中文描述交 dense。hybrid 各司其职
2. char n-gram：无依赖，但索引大、精度一般
3. jieba 分词：中文效果好，加轻依赖

起步用方案 1——hybrid 已让 dense 管中文语义，BM25 不必再卷中文。

### 5.3 prompt 规则强化

`search_tool_rail.py:96` 的 `_RULES_CN` 现在只说"对话历史里已有 schema 就别重搜"。应补一条：

> **系统提示/导航里已给出完整描述和参数的工具，可直接按名调用，不必先 search_tools。**

`send_file_to_user` 在 `prompt_builder.py:246` 的「文件发送」章节已有完整描述，模型其实根本不需要 search，直接按名调即可。这条规则能省掉无效搜索。

## 六、与 ratel-ai/ratel 的对比

### 6.1 ratel 简介

- **定位**：独立的 context engineering 层（Rust 引擎 + TS/Python SDK），不是 agent 框架
- **仓库**：https://github.com/ratel-ai/ratel
- **核心**：`ratel-ai-core`（Rust）+ `@ratel-ai/sdk`（TS）+ `ratel-ai`（Python），in-process，无 vector DB
- **检索**：BM25（默认）/ semantic / hybrid（RRF 融合），per-call 可选
- **capability tools**：`search_capabilities` / `invoke_tool` / `get_skill_content`
- **官方文档**：https://docs.ratel.sh

### 6.2 关键对比

| 维度 | ratel | 我们 |
|---|---|---|
| **检索默认** | BM25（无模型、快、确定性、永不失败） | dense embedding（BAAI/bge-small-zh） |
| **hybrid** | 已实现（BM25+dense RRF，ADR-0011） | 只有 dense + 手工 boost，BM25 是 TODO |
| **haystack** | 精细：拆 snake_case + 排 JSON 噪音 + 索引 enum | 粗糙：raw dict 整段塞（含 JSON 噪音） |
| **boost** | 无手工规则，靠 BM25 IDF | `VERB_INTENT` 中英动词映射 + name 子串 boost |
| **tools[] 策略** | capability-tools-only 模式恒定 / replace 模式每轮变 | 全程恒定（基座+入口） |
| **prefill/kv-cache** | capability-tools-only 模式：恒定，命中 | 恒定，命中（**等价**） |
| **调用路径** | `invoke_tool` by id（通用兜底）/ 按名直调（框架支持时） | 按名直调（ability_manager，无中介） |
| **prompt 地图** | 无，agent 只看 search_capabilities | 有"导航+隐藏摘要+规则"三段注入 |
| **ghost 过滤** | 无（用户显式 register） | 有（双注册表代价） |
| **min_sim 阈值** | 无 | `min_sim=0.35` |
| **skill 层** | 一等公民（SkillRegistry + get_skill_content） | 分开（Symphony 编排） |
| **生态** | Rust + TS/Python SDK，跨框架 | 纯 Python，绑 openjiuwen |
| **MCP** | 双向，旗舰场景 | 有配置非核心 |
| **telemetry** | 完整 OTel + usage 学习 | 弱，debug trace |

### 6.3 两个设计哲学

- **ratel**：工程性优先（零依赖、跨框架、确定性、快）。假设"工具检索是通用问题，BM25 + 干净文本就够"。
- **我们**：模型引导优先（prompt 地图、tools[] 全程恒定保 cache、中文语义）。假设"工具检索要配合 prompt 注入和 cache 策略一起设计"。

### 6.4 可借鉴的 3 点

1. **haystack 干净化**（坑 3）：拆 snake_case + 排 JSON 噪音 + 索引 enum——直接改 `haystack_for`
2. **hybrid RRF 融合**：BM25 + dense 用 RRF，per-call 选——文档里"后续引入 BM25 混合检索"的现成模板
3. **`(score desc, id asc)` 全量排序后截断**：把"top-K membership 跨进程稳定"当正式契约守（ratel 有专门测试）

### 6.5 cache 维度的澄清

之前对比曾误把 ratel 的 `replace` 模式（每轮 tools[]=top-K，破 cache）当成它的主要模式。实际上 ratel 官方推荐（llms.txt 标 ✅ right）的 `capability-tools-only` 模式 tools[] 恒定 = `[search_capabilities, invoke_tool]`，prefill 恒定，kv-cache 命中——**和我们等价**。`replace` 只是 opt-in 替代。在 cache 保活上两边打平。
