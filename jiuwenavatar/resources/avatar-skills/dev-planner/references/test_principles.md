# 测试计划原则

> 你需要作为**研发计划工程师（测试侧）**，基于 `doc/<module>/requirements.md`、`doc/<module>/design.md` 与 `doc/<module>/dev_plan.md`，将设计与开发任务映射为分层、可执行的测试 checklist，并写入 `doc/<module>/test_plan.md`。
>
> 本文档定义测试规划方法论、执行策略、覆盖率目标与验收标准。
>
> **落盘结构唯一来源**：`test_plan_template.md`；**门禁**：`check_plan.py --plan test`。本章只规定映射与填写规则，不重复模板正文。开发侧见 [dev_principles.md](dev_principles.md)。

## Skill 定位

```
用户/Issue → leader → [analyzer] → requirements.md → [designer] → design.md → [planner] → test_plan.md → [coder] → [tester] → [reviewer]
                                                                                      ▲
                                                                            本阶段·测试计划（agent planner）
```

- **上游输入**：`requirements.md`（验收标准）、`design.md`（测试模型、正确性属性）、`dev_plan.md`（开发任务块）
- **输出**：`doc/<module>/test_plan.md`（Markdown checklist，初始态全部 `[ ]`）
- **下游**：测试工程师按 checklist 编写与执行测试；coder 随开发同步完成对应测试

## 前置条件

1. 已完成需求分析与架构设计，`requirements.md` 与 `design.md` 可读
2. 已阅读 `design.md` 中的测试模型、正确性属性、边界条件与异常场景设计
3. 已理解 `dev_plan.md` 中的开发任务划分（或在与 dev_plan 同时生成时保持任务块对齐）
4. 如需代码上下文，确保本地仓库已 clone 且现有测试结构可读

## 1. 测试规划方法论

### 1.1 测试规划原则

1. **分层覆盖**：单元测试 → 属性测试 → 集成测试 → 端到端测试，逐层覆盖
2. **按任务映射**：每个开发任务至少对应一个测试任务
3. **覆盖率要求**：参照项目代码开发规范（总体 ≥ 80%，核心模块 ≥ 90%，新增代码 100%）
4. **测试命名**：遵循 `test_<module>_<scenario>` 规范
5. **正确性属性**：`design.md` 中标注的正确性属性，必须生成属性测试任务块
6. **同步规划**：测试计划与开发计划同步产出，不建议开发完成后再补测试

### 1.4 机制测试优先（新增）

- 对 Shell/IO/超时类问题，优先规划机制验证，再做返回格式断言。
- 禁止把“字段存在/字符串包含”当作唯一验证证据。
- 建议覆盖：超时/取消、超大输出、双流时序、进程残留、交互式命令阻断。
- 若仅做上层 mock 验证，必须在任务描述标注“未验证底层机制”。

### 1.2 测试类型定义

| 测试类型 | 范围 | 典型验证内容 |
|---------|------|-------------|
| 单元测试 | 单个函数/类 | 输入输出、边界、异常分支 |
| 属性测试 | 正确性属性 | design.md 中的不变量、等价关系 |
| 集成测试 | 模块间交互 | 服务协作、数据流、依赖注入 |
| 端到端测试 | 完整流程 | API 全链路、用户场景 |
| 回归测试 | 已有功能 | 确认未引入回归 |

### 1.3 测试任务字段语义

虽然 `test_plan.md` 使用 checklist 而非 TT-XXX 表格，但每个测试任务块在语义上应包含：

| 字段 | 说明 | checklist 体现方式 |
|------|------|-------------------|
| 测试编号 | 唯一标识 | 层级编号 `1.`、`1.1`、`3.2` |
| 对应开发任务 | 与 dev_plan 对齐 | 顺序与编号对应；`_依据：dev_plan §x_` |
| 测试类型 | 单元/属性/集成/端到端 | 任务标题或子任务标注 |
| 测试文件 | 测试代码路径 | 子任务中写明 `tests/test_xxx.py` |
| 测试要点 | 验证什么 | 子任务描述 + `_依据：..._` |

## 2. 测试计划流程

### 2.1 标准计划流程

```
设计解析 → 开发任务对齐 → 测试识别 → 分层编排 → 属性映射 → 文档生成
```

1. **设计解析**：从 `design.md` 提取测试模型、正确性属性、边界与异常场景
2. **开发任务对齐**：按 `dev_plan.md` 任务块逐一映射测试
3. **测试识别**：为每个开发任务确定单元/集成/端到端测试范围
4. **分层编排**：按 1.1 节分层原则排列测试任务，插入测试检查点
5. **属性映射**：将 design.md 正确性属性转为属性测试任务块
6. **文档生成**：按 `SKILL.md` 格式生成 `test_plan.md`

### 2.2 测试计划检查清单

- [ ] 每个开发任务至少有一个对应测试任务
- [ ] `design.md` 中的正确性属性均已映射到属性测试
- [ ] `requirements.md` 中的关键验收条款均有测试覆盖
- [ ] 单元、属性、集成、端到端各层均有规划（可按项目裁剪）
- [ ] 异常、边界和回归测试已覆盖
- [ ] 测试检查点与最终验收检查点已设置
- [ ] 测试覆盖率目标可满足项目要求
- [ ] 测试任务顺序与 dev_plan 对应块对齐

## 3. 测试风险评估

### 3.1 测试难度风险

| 等级 | 描述 | 处理方式 |
|------|------|---------|
| 高 | 场景复杂、依赖外部服务、难以构造测试数据 | 提前规划 mock/fixture，单独测试检查点 |
| 中 | 模块间交互多，集成测试编排复杂 | 明确测试数据与隔离策略 |
| 低 | 纯函数或独立模块，易于单测 | 随开发同步完成 |

### 3.2 风险识别要点

- **覆盖缺口风险**：开发任务无对应测试
- **属性遗漏风险**：正确性属性未转为属性测试
- **环境依赖风险**：测试依赖特定环境或外部服务
- **回归风险**：修改影响面广但未规划回归测试

## 4. 测试计划编排

### 4.1 测试任务列表（语义结构）

对应 dev-planner 的 TT-XXX 表格，在 checklist 中体现为：

| 测试编号 | 对应开发任务 | 测试类型 | 测试文件 | 测试要点 |
|---------|------------|---------|---------|---------|
| 2.1 | dev 2.1 | 单元测试 | `tests/test_user_model.py` | User 实体字段校验、序列化 |
| 3.1 | dev 3.x | 属性测试 | `tests/test_user_props.py` | 属性 1：id 唯一性 |
| 5.1 | dev 5.x | 集成测试 | `tests/test_user_api.py` | 创建用户全链路 |

一个开发任务可对应多个测试任务（如单元 + 集成）。

### 4.2 测试执行策略

在「概述」或「注意事项」中说明执行时机：

- **随开发执行**：每完成一个开发任务块后，立即执行对应的测试任务
- **集成验证**：相关模块开发完成后，执行集成测试与端到端测试
- **回归验证**：全量执行已有测试用例，确认未引入回归
- **检查点驱动**：在测试检查点处汇总执行阶段性测试套件

在固定小节 `## 可并行组（G5）` 中说明 G5 tester 并行指导信息：

- 有安全并行空间时，写 `- PG-N: items [<测试任务编号...>] | maps dev [<开发任务编号...>] | touch: `<测试路径...>``
- 无安全并行空间时，写 `无（serial）`
- `items` 必须引用 `## 测试任务` 中实际存在的 checklist 编号
- `maps dev` 应优先与 `dev_plan.md` 的 G4 `PG-*` 对齐；无法一一对应时说明映射范围
- `touch` 为测试文件或夹具路径，不同 PG 不得重叠
- 默认 `max_shards = 3`；共享 fixture、共享外部服务或顺序依赖明显时保留 serial

示例：

```markdown
## 可并行组（G5）
- PG-1: items [2.1, 2.2] | maps dev [3.1, 3.2] | touch: `tests/test_gateway.py`
- PG-2: items [4.1] | maps dev [4.1] | touch: `tests/test_service_flow.py`
```

### 4.2.1 执行范围

`## 可并行组（G5）` 之后追加 `## 执行范围`：

- `G5 本轮回`：PG 全部 items，或 serial 时 Leader 列出的编号。
- `G5 延后`：集成、E2E、回归、§9–§10 验收等；写明 G5-serial、人工或 G6 前收口。
- PG items 不得只写在 PG 却标为延后。

### 4.3 覆盖率目标

| 范围 | 目标覆盖率 | 说明 |
|------|-----------|------|
| 总体 | ≥ 80% | 项目基准要求 |
| 核心模块 | ≥ 90% | design.md 中标注的核心模块 |
| 新增代码 | 100% | 本次新增的所有代码 |

### 4.4 必须覆盖的测试类别

复制 `test_plan_template.md` 时须保留 **9 个顶层任务分类**（语义与模板一致）；`check_plan.py --plan test` 会按标题校验。须将 `design.md` 的 `## 正确性属性` 映射为「属性测试」块；可合并子任务，**不得**删除顶层分类行。

当需求涉及基础设施层时，`test_plan.md` 需补充「机制测试」任务块，至少包含一条与机制行为相关的检查点（如超时保真、进程清理）。

### 4.5 概述章节内容要求

「概述」应包含：

- 测试范围（覆盖哪些模块、哪些 dev_plan 阶段）
- 测试分层策略（单元/属性/集成/端到端的比重）
- 主要测试风险（环境依赖、复杂场景、覆盖率难点）
- 验收方式（覆盖率工具、CI 集成、手动验证项）

> **涉及性：** Feature/Bug/Refactor 类型必填测试任务；Docs 类型若无可执行测试项，在「测试任务」中标注「不涉及」但仍保留章节结构。

## 5. 测试计划输出指导（checklist 映射）

> **重要提醒：**
>
> - 骨架复制 `test_plan_template.md`；所有任务初始为 `[ ]`，不得使用 `[x]`
> - 任务块末尾用斜体追溯：`_依据：requirements.md §x / design.md ## <章节> / dev_plan §x_`
> - `design.md` 的 `## 正确性属性` **必须**生成属性测试块（`- [ ] **属性 N: ...**`）

**属性测试任务块格式（必须）：**

```markdown
- [ ] 3. 属性测试

  - [ ] **属性 1: 用户 ID 全局唯一**
  - [ ] **验证需求：design.md ## 正确性属性；requirements.md SR-005**

  - [ ] 3.1 编写属性测试（`tests/test_user_properties.py`）
  - [ ] 3.2 覆盖边界：空值、重复创建、并发创建

  _依据：design.md ## 正确性属性；dev_plan §2 数据模型_
```

**常规模块示例：**

```markdown
- [ ] 2. 单元测试

  - [ ] 2.1 UserService.create 正常路径（`tests/test_user_service.py`）
  - [ ] 2.2 UserService.create 重复邮箱异常分支
  - [ ] 2.3 UserRepository.save 持久化逻辑

  _依据：dev_plan §3 核心服务层；design.md ## 组件和接口_
```

## 6. 测试验收标准

### 6.1 计划完成标准

- [ ] 每个开发任务有对应的测试任务
- [ ] 所有正确性属性已映射到属性测试
- [ ] 测试分层合理，检查点已标识
- [ ] `test_plan.md` 已生成并落盘

### 6.2 完成标准（与门禁对齐）

- [ ] 每个 dev_plan 顶层块有测试映射；`design.md ## 正确性属性` 均有属性测试块
- [ ] requirements 关键验收点有 `_依据：..._` 追溯
- [ ] `check_plan.py --plan test` 退出码 0 且 stdout 含 `[OK] Validated`

### 6.3 交付验收清单（tester 阶段参照）

#### 测试验收

- [ ] 所有测试任务（checklist 条目）已通过
- [ ] 测试覆盖率达标（总体 ≥ 80%，核心 ≥ 90%，新增 100%）
- [ ] 无跳过的测试用例（或跳过原因已记录）
- [ ] 边界条件和异常场景已覆盖
- [ ] 回归测试通过，未引入新问题

#### 可观测性验证

- [ ] 关键路径日志输出符合设计
- [ ] 监控指标（如有）可采集
- [ ] 错误码与异常响应符合 design.md 约定
