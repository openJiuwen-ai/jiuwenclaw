# 开发计划原则

> 你需要作为**研发计划工程师（开发侧）**，基于 `doc/<module>/requirements.md` 与 `doc/<module>/design.md`，将设计方案拆解为有序、可执行的开发 checklist，并写入 `doc/<module>/dev_plan.md`。
>
> 本文档定义开发计划的方法论、流程规范、执行编排与验收标准。
>
> **落盘结构唯一来源**：`dev_plan_template.md`；**门禁**：`check_plan.py --plan dev`。本章只规定拆解与填写规则，不重复模板正文。测试侧见 [test_principles.md](test_principles.md)。

## Skill 定位

```
用户/Issue → leader → [analyzer] → requirements.md → [designer] → design.md → [planner] → dev_plan.md → [coder] → [tester] → [reviewer]
                                                                                      ▲
                                                                            本阶段·开发计划（agent planner）
```

- **上游输入**：`requirements.md`（需求约束、验收标准）、`design.md`（模块、接口、数据模型、文件修改清单）
- **输出**：`doc/<module>/dev_plan.md`（Markdown checklist，初始态全部 `[ ]`）
- **下游**：开发工程师按 checklist 逐步实现；测试工程师参照 `test_plan.md` 同步验证

## 前置条件

1. 已完成需求分析与架构设计，`requirements.md` 与 `design.md` 可读
2. 如需代码上下文，确保本地仓库已 clone 且代码为最新
3. 已阅读 `design.md` 中的模块划分、接口设计、文件修改清单、数据模型与测试模型
4. 已理解 `requirements.md` 中的 Issue 类型、优先级与验收条款

## 1. 开发计划方法论

### 1.1 任务拆解原则

1. **文件粒度**：每个任务应以文件（或文件内的类/函数）为最小拆解单位，避免跨文件的大任务
2. **原子性**：每个任务完成后应可独立编译/运行，不依赖未完成的后续任务
3. **可验证性**：每个任务应有明确的完成标准和对应的测试用例（在 `test_plan.md` 中映射）
4. **可追溯性**：每个任务应可追溯到 `design.md` 中的具体设计章节（接口、数据模型、算法等）或 `requirements.md` 中的需求条目

**粒度提醒：**

- 避免过粗：一个任务包含大量文件修改
- 避免过细：一个任务只改一行且无独立验证意义
- 若一个逻辑变更涉及多个文件，优先拆为多个有依赖顺序的子任务，而非合并为一个大任务

### 1.2 任务排序原则

1. **依赖优先**：被依赖的模块先于依赖它的模块开发（如数据层 → 业务层 → 接口层）
2. **风险前置**：高风险或高不确定性的任务应尽量靠前，尽早暴露问题
3. **基础设施先行**：公共模块、工具函数、配置变更等基础设施类任务优先
4. **测试同步**：开发任务规划时同步考虑测试映射，不建议开发全部完成后再补测试计划

**分层顺序基线（适用时）**：

`基础设施(IO/进程) → 核心逻辑 → 呈现/Tool → 集成检查`

若需求已定位到 L2/L3（基础设施层），不得把 `_tool.py` 组装任务排在基础设施修复任务之前。

### 1.3 开发任务字段语义

虽然 `dev_plan.md` 使用 checklist 而非 T-XXX 表格，但每个任务块在语义上应包含以下信息（体现在标题、子任务或 `_需求：..._` 引用中）：

| 字段 | 说明 | checklist 体现方式 |
|------|------|-------------------|
| 任务编号 | 唯一标识 | 层级编号 `1.`、`1.1`、`2.3` |
| 任务描述 | 做什么 | 任务标题与子任务描述 |
| 目标文件 | 改哪些文件 | 子任务或标题中写明路径 |
| 修改类型 | 新增/修改/删除 | 子任务描述中标注 |
| 依赖任务 | 前置任务 | 任务顺序 + 检查点 |
| 复杂度 | 高/中/低 | 高风险任务前置或单独成块 |
| 对应详设章节 | 设计追溯 | `_需求：design.md ## <章节>_` |

## 2. 开发计划流程

### 2.1 标准计划流程

```
详设解析 → 任务识别 → 依赖分析 → 排序编排 → 阶段划分 → 文档生成
```

1. **详设解析**：通读 `requirements.md` 与 `design.md`，提取模块、接口、数据模型、文件修改清单
2. **任务识别**：按 1.1 节原则将每个设计点拆解为 checklist 任务
3. **依赖分析**：标注任务间依赖，识别循环依赖并拆分
4. **排序编排**：按 1.2 节原则确定任务顺序，插入开发检查点
5. **阶段划分**：将任务划分为执行阶段（基础设施 / 核心逻辑 / 接口层 / 集成联调）
6. **文档生成**：按 `SKILL.md` 格式生成 `dev_plan.md`

### 2.2 开发计划检查清单

- [ ] `design.md` 中所有模块/接口/数据模型均已对应到开发任务
- [ ] `design.md` 中的文件修改清单均已覆盖
- [ ] 每个任务有明确的输入、输出和完成标准
- [ ] 任务间的依赖关系已识别且无循环依赖
- [ ] 高风险任务已前置或已拆分为更小任务
- [ ] 执行阶段划分合理
- [ ] 关键路径已标识
- [ ] 可并行任务组已识别
- [ ] 开发检查点与最终交付检查点已设置
- [ ] 每个开发任务在 `test_plan.md` 中有对应测试映射（见 test_principles）

## 3. 开发风险评估标准

### 3.1 执行风险等级

| 等级 | 描述 | 处理方式 |
|------|------|---------|
| 高 | 任务涉及核心模块变更或跨模块依赖，失败影响大 | 需单独评审，建议拆分为更小的子任务 |
| 中 | 任务涉及单个模块的非核心变更 | 正常执行，需关注边界条件 |
| 低 | 任务为新增独立模块或简单的配置/文档变更 | 可并行开发 |

### 3.2 风险识别要点

- **依赖风险**：任务依赖其他未完成任务的输出
- **变更范围风险**：单个任务修改文件过多，影响面大
- **兼容风险**：修改可能影响现有功能的正确性
- **测试难度风险**：场景复杂，难以构造测试用例（需与 test_principles 联动）

## 4. 执行计划编排

### 4.1 执行阶段划分

根据任务依赖关系和排序原则，将开发任务划分为执行阶段。在 `dev_plan.md` 的「开发任务」中，用顶层编号分段体现阶段，例如：

**阶段示例：**

| 阶段 | 名称 | 典型内容 |
|------|------|---------|
| 阶段 1 | 基础设施 | 项目结构、依赖、配置、公共工具 |
| 阶段 2 | 数据层 | 数据模型、枚举、持久化 |
| 阶段 3 | 核心逻辑 | 核心服务、业务规则 |
| 阶段 4 | 接口层 | API、对外交互、输入验证 |
| 阶段 5 | 集成联调 | 错误处理、日志监控、开发检查点 |

每个阶段内任务按依赖顺序排列，阶段末尾可插入**开发检查点**任务块。

### 4.2 关键路径与并行

在「概述」或「注意事项」中标识关键路径，并在固定小节 `## 可并行组（G4）` 中标识 G4 并行指导信息：

**关键路径示例：**

```
1. 数据模型 → 2. 核心服务 → 4. API 层 → 10. 最终交付检查点
```

**PG-* 输出规则：**

- 有安全并行空间时，写 `- PG-N: items [<任务编号...>] | touch: `<路径...>``
- 无安全并行空间时，写 `无（serial）`
- `items` 必须引用 `## 开发任务` 中实际存在的 checklist 编号
- `touch` 必须来自 `design.md` 文件修改清单或任务中明确写出的目标文件
- 不同 PG 的 `touch` 路径不得重叠；关键路径、共享核心模块或存在顺序依赖的任务不得放入 PG
- 默认 `max_shards = 3`；超过 3 组时须合并低风险组或保留 serial

**可并行任务组示例：**

```markdown
## 可并行组（G4）
- PG-1: items [1.2, 1.3] | touch: `src/config/options.py`, `src/domain/enums.py`
- PG-2: items [3.1] | touch: `src/infra/gateway.py`
```

并行组内的任务仍各自独立可验证；若无法证明互不干扰，写 `无（serial）`。

### 4.2.1 执行范围

`## 可并行组（G4）` 之后追加 `## 执行范围`：

- `G4 本轮回`：PG 全部 items，或 serial 时 Leader 列出的编号。
- `G4 延后`：未列入 PG 的检查点、交付对账、§6/§8/§9 等；写明 G4-serial 或 G6 前收口。
- PG items 不得只写在 PG 却标为延后。

### 4.3 必须覆盖的开发类别

复制 `dev_plan_template.md` 时须保留 **11 个顶层任务分类**（语义与模板一致）；`check_plan.py --plan dev` 会按标题校验。可合并子任务或在标题末标注 `*可选*`，**不得**删除顶层 `- [ ] N. <分类>` 行。

其中「基础设施层」在基础设施相关 Issue 中不可跳过，至少写明：

- 涉及文件路径（如 `src/.../utils.py`）
- 机制目标（如 IO 保真、进程清理）
- 不涉及时的理由（例如“本次问题明确为 L1 业务逻辑，不涉及基础设施”）

### 4.4 概述章节内容要求

「概述」应包含（可融入一段话，也可分点）：

**Issue 信息（如有）：**

- Issue 编号、标题、类型（Bug/Feature/Refactor/Docs）

**关联文档：**

- 需求分析文档：`doc/<module>/requirements.md`
- 架构设计文档：`doc/<module>/design.md`

**计划概述：**

- 整体开发策略（分几个阶段、预计修改多少文件、核心难点）
- 关键路径摘要
- 主要风险与应对（高风险任务如何前置或拆分）

> **涉及性：** Feature/Bug/Refactor 类型必填开发任务；Docs 类型若无可执行开发项，在「开发任务」中标注「不涉及」但仍保留章节结构。

## 5. 开发计划输出指导（checklist 映射）

> **重要提醒：**
>
> - 骨架复制 `dev_plan_template.md`；所有任务初始为 `[ ]`，不得使用 `[x]`
> - 可选任务标题末尾加 `*可选*`，仍用 `[ ]`
> - 任务块末尾用斜体追溯：`_需求：requirements.md §x / design.md ## <章节>_`

**任务块示例：**

```markdown
- [ ] 2. 数据模型和枚举

  - [ ] 2.1 新增 User 实体模型（`src/models/user.py`，新增）
  - [ ] 2.2 新增 UserStatus 枚举（`src/models/enums.py`，修改）

  _需求：design.md ## 数据模型；requirements.md SR-003_

- [ ] 10. 开发检查点

  - [ ] 10.1 核心服务层编译通过，单元测试可运行
  - [ ] 10.2 接口层联调前冒烟验证
```

## 6. 开发验收标准

### 6.1 计划完成标准

- [ ] `design.md` 中的所有设计点已对应到开发任务
- [ ] 每个任务有明确的目标文件和完成标准
- [ ] 任务依赖关系无遗漏、无循环
- [ ] 执行阶段划分合理，关键路径已标识
- [ ] `dev_plan.md` 已生成并落盘

### 6.2 完成标准（与门禁对齐）

- [ ] `design.md` 设计点已映射到开发任务，且 `test_plan.md` 有对应测试（见 test_principles）
- [ ] 任务可独立执行验证，依赖无环
- [ ] `check_plan.py --plan dev` 退出码 0 且 stdout 含 `[OK] Validated`

### 6.3 交付验收清单（coder 阶段参照）

#### 开发验收

- [ ] 所有开发任务（checklist 条目）已完成
- [ ] 代码符合项目编码规范（参照代码开发规范）
- [ ] 无 lint 错误（flake8/mypy 检查通过）
- [ ] 所有新增/修改的公共 API 有类型注解和 docstring
- [ ] 无硬编码的敏感信息

#### Git 提交（Leader G7a，Aidlc 流水线）

- [ ] `dev_plan` 任务条目不包含「自行 commit/push/建分支」（由 Leader **G7a** 统一执行）
- [ ] 若需 Conventional Commits 或分支命名，写入 dev_plan **备注**供 Leader G7a 参照，不由执行角色跑 Git
