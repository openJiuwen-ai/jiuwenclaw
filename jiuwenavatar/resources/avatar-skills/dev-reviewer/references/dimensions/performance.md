# 性能审查指引（performance）

> **先证据后优化**；审查聚焦是否引入可证实的退化或已知反模式，避免无依据的性能指摘。

## 适用时机

- requirements/design 含 SLA、吞吐、延迟预算
- 列表/报表/批处理、缓存、并发、大文件、前端 LCP/INP 路径
- 怀疑回归：对比变更前后指标或复杂度论证

无性能敏感面时：在 findings 中说明「已扫常见反模式，未深入 profiling」即可。

## 工作流（审查版）

```
1. 界定症状域（首屏 / 交互 / API / 批 job）
2. 从 diff 找数据路径与热路径改动
3. 匹配反模式表 → 分级
4. 建议可验证的修复或测量命令（非空泛「优化一下」）
```

**禁止**：无测量、无复杂度论据的「我觉得慢」作为 Must Fix（除非明显 O(n²) 无界等）。

## 后端 / API

| 反模式 | 信号 | 分级建议 |
|--------|------|----------|
| N+1 查询 | 循环内查库/远程调用 | 热路径 Must Fix |
| 无界拉取 | `findMany()` 无 take/游标 | 列表接口 Must Fix |
| 缺索引 | 新 filter/sort 字段无迁移说明 | 大数据量 Must Fix |
| 同步阻塞 | 热路径重型 CPU/正则/同步 IO | Should Fix → 热路径可升格 |
| 缓存 | 先删缓存后写库、无 TTL 无界 Map | 一致性风险 Must Fix |
| 连接 | 无超时/无限重试/池耗尽 | 稳定性 Must Fix |
| 序列化 | 热路径大对象深拷贝/巨型 JSON | Should Fix |

**量化示例**：「每用户 1 次查询 → 100 用户 101 次」优于「可能有性能问题」。

## 前端 / Web

| 指标 | Good（参考） | 审查关注 |
|------|--------------|----------|
| LCP | ≤ 2.5s | 首屏大图无尺寸/格式优化；阻塞 CSS/JS |
| INP | ≤ 200ms | 主线程 >50ms 长任务；巨型同步渲染 |
| CLS | ≤ 0.1 | 图片无 width/height；晚插内容顶布局 |

| 反模式 | 信号 |
|--------|------|
| 大包体 | 新增大依赖、未 lazy 的重库 |
| 重复渲染 | 内联新对象/函数导致子树全刷 |
| 瀑布请求 | 串行 fetch 可并行 |
| 图片 | 首屏无 `fetchpriority`、below-fold 未 lazy |

## 并发与资源

- 锁粒度过大、死锁顺序、共享可变无保护
- 文件句柄/连接/定时器未关闭 → Must Fix（泄露）
- 线程池/异步：阻塞调用占满 worker → Should Fix

## 性能预算（若项目已定义则对照）

典型参考（以仓库文档为准）：

- 首包 JS gzip、单图体积、API p95、Lighthouse 分数
- CI 已有 `bundlesize` / `lhci` 时：审查注明是否应跑及预期门槛

## 与 `review/result.json`

| 情形 | `category` | 备注 |
|------|------------|------|
| N+1 / 无界查询 | `performance` | 附估算或量级 |
| 缺超时熔断 | `performance` 或 `correctness` | 可导致级联失败 |
| 微优化偏好 | Nice to Have | 无数据不升格 |
| 需求声明 SLA 未达标 | `performance` + 链 requirements | 可联合 spec 维度 |

`testing_and_verification` 中应给出**可执行**测量建议，例如：

```json
{ "item": "对比分页接口 p95", "command": "ab / k6 / APM 查询模板", "reason": "新增无 take 的列表" }
```

## 快速清单

```markdown
- [ ] 数据访问无 N+1、无全表/全量无界拉取
- [ ] 列表/搜索有分页或游标上限
- [ ] 外部调用有超时、重试、限流/熔断（按项目基线）
- [ ] 缓存更新顺序与一致性可解释
- [ ] 热路径无多余序列化/分配/同步阻塞
- [ ] 前端：包体、渲染、图片、请求瀑布已扫
- [ ] 若声明 SLA：有测量或合理复杂度证据
```

## 何时不必深挖

- 冷路径、一次性脚本、测试夹具
- 已有基准证明无回归（在 `evidence` 引用数字）
- 纯文案/配置且不经热路径

仍须在 scope 中**明确排除原因**。

## 审查者自省

| 误区 | 纠正 |
|------|------|
| 「我机器上很快」 | 以用户环境、数据量级为准 |
| 「先上再优化」 | 明显反模式应在合并前修 |
| 「到处 memo」 | 过度 memo 亦债；要对症 |

## 与 spec / code 的衔接

- requirements 中的性能 AC 未满足 → 优先 Must Fix（见 `spec.md`）
- 为性能牺牲可读性 → 须在说明中交代测量；否则按 `code.md` 权衡
