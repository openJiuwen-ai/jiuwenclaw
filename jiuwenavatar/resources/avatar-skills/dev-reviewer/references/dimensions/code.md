# 代码质量审查指引（code）

> 审查时对照 diff 与项目既有模式，在**行为不变**前提下评估正确性、可读性、架构与可维护性。

## 适用时机

- 所有实现类 diff（与 `spec.md` 文档对齐审查并行）
- 返工轮：核对修复是否引入新复杂度或行为漂移
- diff 过大时：优先 hotspots，本指引用于**逐文件扫读**时的 mental model

## 审查顺序（建议）

1. **读懂意图** — 变更描述 / Issue / `summary.change_intent` 是否自洽
2. **先看测试** — 测的是行为还是实现细节？边界与失败路径是否覆盖？
3. **再走五轴** — 正确性 → 可读性 → 架构 →（安全/性能见专篇）→ 验证故事
4. **分级落项** — Must Fix / Should Fix / Nice to Have，避免「全是建议」

## 正确性（Correctness）

| 检查项 | Must Fix 信号 |
|--------|----------------|
| 与声明行为一致 | 主路径与测试/注释描述不符 |
| 边界与空值 | null/空集合/0/超长/非法枚举未处理 |
| 错误路径 | 仅 happy path；异常吞掉或错误码不一致 |
| 状态与并发 | 竞态、可见性、重复提交/重试不安全 |
| 兼容 | 破坏 API 字段、序列化、DB schema 且无迁移说明 |

**量化优于模糊**：「列表 100 项时 N+1 约 +50ms/项」优于「可能慢」。

### 数据流深度分析（必做）

对每个被修改的函数，**必须**追踪数据从入口到出口的完整路径，回答以下问题：

1. **输入 → 转换 → 输出**：数据经过了哪些中间步骤？每步的输入/输出分别是什么类型？
2. **数据丢失风险**：字符串操作（`split`/`join`/`strip`/`replace`/regex）、集合操作（`filter`/`map`/`dict.get` 默认值）是否可能**静默丢弃有效数据**？
3. **匹配失败风险**：`if`/`elif`/`match` 是否存在未覆盖的合法输入？`else` 分支是否**吞掉了未预期的数据而非报错**？
4. **中间状态不一致**：多步操作（写 A → 写 B → 写 C）中，某一步失败时**前面的修改是否已持久化**？有无事务/补偿/回滚？
5. **隐式依赖**：函数是否依赖外部状态（全局变量、类属性、文件存在性、环境变量）？这些依赖不可用时会发生什么？

**审查产出要求**：发现数据流问题时，finding 必须写清**具体场景**（如「当 section header 为 `_description_` 且正文也包含 `_description_` 字样时，`split` 会误删正文中的有效内容」），而非泛泛的「数据处理不安全」。

### 边界条件与失效模式（必做）

对每个**条件分支**，必须穷举所有可能的输入组合：

1. **空值/零值/极值**：传入 `None`/`""`/`[]`/`0`/`负数`/`超长字符串`/`非法枚举` → 函数行为是什么？是返回合理错误还是崩溃/静默出错？
2. **外部依赖失效**：LLM 返回空/Malformed JSON、API 超时/返回 5xx、文件不存在/权限不足、DB 连接断开 → 代码如何处理？有没有重试/降级/报错？
3. **异常处理质量**：`try/except` 是否过于宽泛（`except Exception` 吞掉所有错误）？异常日志是否包含足够上下文（traceback、输入参数）？异常后系统是否处于一致状态？
4. **并发/竞态**：多线程/多进程/多请求同时执行时，共享状态是否安全？是否有「check-then-act」的 TOCTOU 问题？

**审查产出要求**：发现边界问题时，必须给出**触发条件**（什么输入/什么状态会触发），并给出**实际后果**（数据丢失、崩溃、安全漏洞、静默错误），而非泛泛的「边界处理不全」。

### 向下兼容与语义变更（必做）

对**任何修改现有行为**的变更：

1. **调用方影响**：旧调用方依赖旧行为 → 改了之后会怎样？是编译/运行时错误，还是静默行为变化？
2. **API/数据格式变更**：字段重命名/删除/类型变更、序列化格式变化、DB schema 变更 → 有无迁移说明？有无向后兼容策略？
3. **语义一致性**：新行为是否与函数名/类名/文档注释仍一致？不一致 → 是代码错了还是文档/命名需要更新？
4. **破坏性变更识别**：若变更会破坏现有功能，必须标为 Must Fix 并要求提供迁移方案或兼容层。

**审查产出要求**：发现兼容性问题时，必须指明**哪些现有代码/API 消费者会受影响**，以及**影响的严重程度**（编译错误/运行时崩溃/静默行为变化），而非泛泛的「可能有兼容性问题」。

## 可读性与简化（Readability & Simplification）

**原则**：简化目标是**更快被理解**，不是更少行数。未理解代码前不要建议大改。

| 模式 | 通常 Should Fix | 通常 Must Fix |
|------|-----------------|---------------|
| 命名 | `data`/`result`/`temp` 无上下文 | 名称与行为相反（如 `get` 却写库） |
| 控制流 | 3 层以上嵌套、嵌套三元 | 逻辑分支遗漏导致错误行为 |
| 函数体量 | 50+ 行多职责 | 单函数混合互斥业务导致难测难改 |
| 重复 | 5+ 行重复未抽取 | 复制粘贴导致一处修了另一处仍错 |
| 死代码 | 未使用 import/分支 | 误导性遗留 API 仍被调用 |
| 「聪明」写法 | 链式 reduce/密集三元 | 掩盖错误处理或改变求值顺序 |

**简化红线（禁止在审查中鼓励）**：

- 为少行数删除或弱化错误处理
- 未跑通测试就建议「顺手重构」无关文件
- 破坏项目约定（import 风格、错误处理模式）的「个人偏好」

**Chesterton's Fence**：建议删除抽象/分支前，先问「为何存在」；无证据则标 Should Fix 并建议作者说明。

## 架构（Architecture）

- 是否遵循仓库既有分层（handler / service / domain），还是业务散落在入口层？
- 新模式是否必要？若引入新模式，是否一处示范、边界清晰？
- 依赖方向：避免循环依赖；领域层不应依赖 UI/框架细节
- 抽象是否**第三次用例**才值得？过早泛化 → Should Fix
- 特性与重构是否混在同一 diff？应建议拆分（见变更体量）

## 变更体量与描述

| 行数（约） | 建议 |
|------------|------|
| ~100 | 理想，可一次审完 |
| ~300 | 可接受，须单一逻辑主题 |
| ~1000 | 要求拆分或声明仅做意图核对（删库、机械重构） |

变更说明第一行须**独立可读**（祈使、说明「做什么」）；正文写**为何**、取舍、链接 Issue/基准。

## 依赖

新增依赖前问：现有栈能否解决？体积、维护度、`audit`、许可证。审查中：**无必要的新依赖** → Should Fix；**已知高危 CVE 且可达** → Must Fix。

## 与 `review/result.json` 的映射

| 维度 | `category` 建议 |
|------|-----------------|
| 逻辑错误 | `correctness` |
| 可读/重复/命名 | `maintainability` |
| 缺测/测错对象 | `testing` |
| 模块边界 | `maintainability` |

## 快速清单

```markdown
- [ ] 意图与测试一致，边界/错误路径有覆盖
- [ ] 命名与项目风格一致，无误导性「聪明」代码
- [ ] 职责清晰，无不当跨层或循环依赖
- [ ] 无死代码/无意义抽象；重复逻辑已收敛或已说明
- [ ] 变更规模可审；说明与 diff 自洽
- [ ] 验证故事完整（测了什么、如何手动验证）
```

## 常见误判（审查者自省）

| 说法 | 事实 |
|------|------|
| 「测试过了就行」 | 测不出架构债、部分安全与可读性问题 |
| 「不是我写的风格」 | 风格指南优先；整体健康改进应通过 |
| 「以后重构」 | 审查是质量门；能小步修的应在合并前修 |
| 「AI 写的应该没问题」 | 需**更多**证据，非更少 |

## 批准标准（与 dev-reviewer 一致）

在**无 Must Fix** 且明显提升或可接受地维持代码健康时，可 PASS；不必追求完美。不应因「不是我会怎么写」而阻塞合理改进。
