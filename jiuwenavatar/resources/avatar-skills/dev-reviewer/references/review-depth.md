# Review Depth Requirements

代码审查不能停留在命名、函数长度、注释风格等表面问题。每条 Must Fix / Should Fix 必须写明具体场景和可验证修复方向。

## 数据流追踪

对每个被修改函数/方法追踪输入到输出：

- 输入从哪里来，经过哪些转换/过滤，最终落到哪里。
- 是否存在静默丢失：匹配失败、异常吞掉、条件分支未覆盖。
- 是否存在中间状态不一致：A 写成功但 B 写失败，无回滚或补偿。
- 字符串/集合操作是否误丢数据：`split` / `join` / `strip` / `filter` 等。

## 边界与失效模式

对每个分支条件追问输入组合：

- 空值、空集合、零、负数、超长字符串、非法枚举。
- 外部依赖返回异常、超时、空结果。
- `try/except` 是否过宽，异常是记录、传播、补偿，还是吞掉。
- 错误路径是否只写日志但业务状态已经不可恢复。

## 兼容性与语义变更

对每个修改现有行为的变更确认：

- 旧调用方是否依赖旧返回值、旧字段、旧异常、旧序列化格式。
- API 字段、DB schema、配置键、事件格式是否变更；是否需要迁移说明。
- 新语义是否仍符合函数名、注释、文档和需求。

## 系统性覆盖

从功能整体扫描输入、处理、存储、输出：

- 是否只改了一个环节但上下游没跟上。
- 是否存在组合运行时才暴露的问题。
- 关键路径、异常路径、边界路径是否都有测试或等价验证。

## 输出标准

- `issue` 写具体触发条件，不写“代码质量不好”。
- `risk` 写真实影响：数据、业务、稳定性、安全、性能或维护成本。
- `recommendation` 写修哪里、怎么修、补什么验证。
- 未读对应维度参考却引用其条款时，在 `limitations` 登记并降级为 Should Fix。
