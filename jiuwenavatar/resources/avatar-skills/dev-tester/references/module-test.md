# 模式 A：模块测试计划（`test_plan.md`）

在 **Aidlc 流水线** 或用户明确要求按模块测试计划执行时使用本路径。

## 第一步

1. 用一句话复述用户期望达成的结果。
2. 明确模块名，并读取 `doc/<module>/test_plan.md`；若无法从上下文判断模块名，先询问。
3. **解析 Python 环境**：见 `skills/env-setup/references/python-env.md`。
4. **解析 Node.js 环境**：见 `skills/env-setup/references/node-env.md`。
5. 在提出方案之前，用 Read 或 `tester_plan_check.py ... status` 查看待办与已完成 checklist，并阅读相关源码、现有测试、配置与近期报错。
6. 明确可被验证的成功标准（测试、构建、Lint，或可执行的实操验收）。
7. 仅在歧义会影响实现方式、安全边界或对用户的对外行为时再追问。

很小的改动可在编辑前用一两句话带过；涉及面广或架构类任务则简要对齐方案并点明取舍。

## 测试流程

非平凡任务可按此循环：

1. 读取 `doc/<module>/test_plan.md`，确认当前要执行的未完成 checklist 任务。
2. 在 **`$PYTHON`（项目 venv）** 中安装缺失测试依赖（若需要），再执行计划中的测试命令（遵守 [SKILL.md](../SKILL.md)「命令超时」节）。
3. 探索足够上下文以把握归属、风格与测试习惯。
4. 简短列出方案与验证步骤。
5. 改动最少的一组文件。
6. 在虚拟环境内先做针对性校验；风险或共享行为大时再扩大验证范围。
7. 验证失败时依据报错迭代，用证据而非猜测。
8. 执行 AC→机制行为映射：逐条确认验收项对应的机制证据（如超时保真、进程清理）；若仅 mock 上层响应，记录“未验证底层机制”。
9. 验证通过后，在 `test_plan.md` 勾选对应项；子项全勾后同步勾父项。
10. 收尾说明改动、可复现验证命令与退出码/摘要、剩余风险；运行 `tester_plan_check.py ... verify`。

多步骤任务若宿主支持待办列表，用它来跟进；同一时间只标记一项为进行中。

## test_plan.md 更新规则

`test_plan.md` 是测试进度的来源。更新时保持 `Planner` 生成的 Markdown 格式不变：

- 只勾选本次已验证的任务；保持 Planner 格式，勿重排编号、标题或需求引用。
- 子项全勾后同步勾父项。
- `status` 查进度；收尾运行 `verify`。报错则修正后重跑。
- 部分完成、`*可选*` 未验证或属性/集成测试只覆盖部分场景时保留 `[ ]`，只勾已完全覆盖的子项，并在回复中说明剩余工作。
- 计划与实现不一致时先说明；仅经确认或明显笔误才改任务描述。

## Aidlc 团队边界

在 `aidlc-dev-team` 中执行本模式时：

- 对 `test_plan.md` **负最终勾选责任**；未跑或无法跑时不得勾 `[x]`。
- **禁止**私自调用 GitCode Issue/MR API 或经手令牌；Issue/PR 正文仅使用 Leader 提供的快照。
- 可与 **coder** 直接对齐复现、fixture、环境与预期；门禁结论、豁免与文档四角色问题须 **汇报 Leader**。
- Gate Verdict：`PASS` | `REWORK`（非 PR 子流程的 PASS/FAIL）。

## 与 PR 门禁证据衔接

若同一任务还执行了 [pr-unit-test-gate.md](pr-unit-test-gate.md)，将 `<REPORT_DIR>/report.md` 摘要写入 Evidence；仅当 `test_plan` 中对应项已被 runner 用例覆盖且通过时，才把 checklist 勾为 `[x]`。

## 收尾自检（模块模式）

- 是否已读够代码，避免瞎猜？
- 是否已读取 `doc/<module>/test_plan.md` 并按计划执行？
- 测试是否在项目虚拟环境（`$PYTHON`）中执行并留有证据？
- 完成且验证过的测试计划任务是否已在 `test_plan.md` 中标记为 `[x]`？
- 每条机制相关 AC 是否有对应命令与结果证据？
- 是否避免了覆盖用户工作区、泄露密钥或改动无关内容？
