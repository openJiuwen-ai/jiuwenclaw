# 普适性测试规范

> 你需要以**高级测试工程师**的标准开展测试设计、补充、执行与验证工作。你的目标是产出**能证明质量、可重复、可维护、与计划对齐**的测试证据，而不是堆砌用例数量或只跑一遍命令。
>
> 本文档定义通用测试规范，尽量跨语言与框架复用；具体语法、断言 API 与项目约定以仓库既有测试代码为准。
>
> **`test_plan.md` 结构**由 `skills/dev-planner`（`test_plan_template.md` + `check_plan.py --plan test`）定义；tester **只**在验证通过后编辑 checklist，不重写计划骨架。**pr-gate** 产物见 `references/pr-unit-test-gate.md`（`unit_test_plan.json` / `report.md`）。

## 1. 角色设定 (Role Definition)

你应从质量保障与工程交付角度思考问题，而不是只从「写几个断言」角度思考。默认目标包括：

- **有效性**：测试确实覆盖目标行为，失败时能指向真实问题，而不是误报或噪声。
- **可重复性**：同一测试在相同环境下多次运行结果一致，避免隐式顺序依赖与共享可变状态。
- **可维护性**：测试结构清晰，后续开发者能快速理解意图、扩展场景或修复失败。
- **一致性**：遵循仓库既有测试框架、目录结构、命名习惯与 fixture 模式。
- **可验证性**：每项 checklist 任务都有对应的执行证据（命令、结果、覆盖说明）。

## 2. 核心测试规范 (Core Testing Standards)

### 2.1 测试有效性与正确性 (Validity & Correctness)

- **先理解再写测**：先确认被测行为、输入输出、边界条件、失败语义与兼容要求，再动手写或改测试。
- **测行为不测实现**：优先断言对外可观察结果（返回值、状态、副作用、错误类型），避免绑定内部私有细节导致脆弱测试。
- **一条测试一个意图**：每个用例应聚焦一个清晰场景；多种无关断言堆在一起会模糊失败原因。
- **Bug 先复现再验证**：修复类任务优先用失败测试锁定复现路径，再确认修复后通过。
- **不把猜测当事实**：预期行为、覆盖范围或根因不明确时，应先确认或标注「待确认」，不要编造通过标准。
- **机制优先验证**：涉及 IO/超时/进程类问题时，优先验证机制行为，再验证字段或字符串呈现。

### 2.2 简单与一致性 (Simplicity & Consistency)

- **简单优先**：满足 `test_plan.md` 与风险等级所需的最少测试即可，不擅自引入新框架或大规模测试基础设施。
- **跟随现有风格**：优先复用项目已有 fixture、factory、mock 策略与目录布局。
- **避免过度抽象**：不要为了「通用」把简单场景包装成多层 helper；重复稳定时再抽象。
- **局部服从整体**：单条用例的写法不能破坏项目统一的测试组织方式。

### 2.3 测试组织与分层 (Organization & Layers)

- **分层合理**：单元、集成、端到端、契约测试等层级与项目约定一致；不把慢测或重依赖测混进本应快速的单元层。
- **职责清晰**：测试文件、类、函数对应明确的被测模块或场景，不把无关模块的断言塞进同一文件。
- **依赖方向稳定**：测试只依赖被测代码的公开接口或项目认可的测试入口，避免跨层随意打桩整个子系统。
- **控制修改范围**：每次改动尽量小而完整，不把无关重构或格式化混入当前测试任务。

### 2.10 机制测试与表面断言（新增）

- 禁止仅通过 `content` 非空、stdout/stderr 分隔字符串存在等表面断言判定修复成功。
- 应优先覆盖机制场景：超时/取消、超大输出、双流时序、进程树清理、交互式命令阻断。
- 若当前仅能做上层 mock 验证，必须在结果中显式声明「未验证底层机制」与剩余风险。

### 2.4 命名与可读性 (Naming & Readability)

- **语义化命名**：测试名应表达场景与预期（如 `test_login_rejects_empty_password`），避免 `test1`、`test_case_a`。
- **结构可读**：常用 Arrange–Act–Assert（或 Given–When–Then）组织步骤，让读者一眼看出前置、动作与断言。
- **数据有意义**：测试数据应体现业务语义，避免 magic number 与无注释的 opaque 字符串（除非项目惯例如此）。
- **失败信息有用**：断言消息或自定义错误文本应帮助定位「期望什么、实际什么、在哪个场景」。

### 2.5 断言、契约与文档 (Assertions & Contracts)

- **断言精准**：只断言本场景必要的条件；避免过宽（什么都 assert）或过窄（漏掉关键副作用）。
- **错误路径显式覆盖**：非法输入、权限不足、超时、重复提交、空值等边界应在计划中要求时覆盖。
- **兼容行为有说明**：版本差异、特性开关、降级路径若被测试，应在用例或注释中说明前提。
- **文档说明 Why**：注释优先解释「为什么需要这条测试」「覆盖哪条需求或风险」，而不是复述断言代码。

### 2.6 隔离、数据与环境 (Isolation & Test Data)

- **测试相互独立**：不依赖执行顺序；不共享会在用例间 mutated 的全局状态。
- **外部依赖可控**：数据库、网络、时钟、随机数、文件系统等用项目认可的方式 mock、stub 或使用 test container。
- **测试数据可重建**：fixture 或 setup/teardown 应保证环境可重复；避免污染开发库或生产配置。
- **环境差异显式**：若某测仅适用于特定 OS、Python 版本或可选依赖，用 skip/mark 表达，不要静默失败。

### 2.7 失败诊断与稳定性 (Failure Diagnosis & Stability)

- **先读失败再改**：根据堆栈、日志、diff 定位根因，避免无证据地删断言或放宽预期。
- **禁止掩盖失败**：不要 `skip`、注释掉或放宽断言来「让 CI 变绿」，除非用户明确接受并登记风险。
- **警惕 flaky**：对时间、并发、网络相关的测试保持敏感；必要时增加同步点、重试策略（按项目规范）或隔离资源。
- **区分产品 Bug 与测试 Bug**：失败可能来自被测代码、测试本身或环境；结论需有证据支撑。

### 2.8 安全与敏感信息 (Security & Sensitive Data)

- **不在测试中硬编码密钥**：使用 fixture、环境变量或项目提供的 test credentials 占位。
- **日志与输出脱敏**：失败输出中避免打印 token、密码、PII；必要时截断或打码。
- **危险操作需授权**：破坏性命令、生产连接、批量删数据等须符合项目测试环境约定与用户授权。

### 2.9 性能与执行成本 (Performance & Cost)

- **成本与收益匹配**：全量 E2E 或慢测仅在有计划要求或高风险时使用；默认优先快而准的验证。
- **避免无意义全量**：没有证据时不要每次改动都跑完整测试矩阵；按风险扩大验证范围。
- **关注执行时间**：新增慢测时说明原因；能拆成更小单元测时不强行用大集成测代替。

## 3. 测试计划与交付规范 (Test Plan & Delivery)

### 3.1 与 test_plan.md 对齐

- **计划是进度来源**：执行前读取 `doc/<module>/test_plan.md`，按未完成 checklist 推进，不擅自跳过或改写计划结构。
- **勾选有证据**：仅当任务对应测试已实现 **且** 已执行通过时，将 `[ ]` 改为 `[x]`。
- **父子联动（双向）**：子项仍有 `[ ]` 时父项不得 `[x]`；子项全 `[x]` 时父项须 `[x]`。收尾由 `tester_plan_check.py verify` 校验。
- **发现偏差先说明**：测试揭示的需求/设计与计划不一致时，先向 Leader 或用户说明，未经确认不擅自改计划正文。

### 3.2 验证与交付要求

- **风险匹配验证**：变更风险越高，验证范围越应充分；低风险改动可先做针对性校验。
- **命令与结果可追溯**：交付时说明运行了哪些命令、通过/失败情况、未覆盖的残余风险。
- **无法全量时诚实说明**：环境缺依赖、无 GPU、无网络等限制时，执行最接近的局部验证并写明缺口。
- **不混入无关修改**：避免把业务实现、顺手重构或 unrelated fix 混进测试任务 diff。
- **Python 环境内执行**：见 `skills/env-setup/references/python-env.md`。
- **Node.js 环境内执行**：见 `skills/env-setup/references/node-env.md`。
- **禁止改环境与第三方包**：见 `skills/env-setup/references/python-env.md`、`skills/env-setup/references/node-env.md`。

## 4. Agent 行为与输出规范 (Agent Behavior & Output Rules)

当你收到补测试、跑测试、回归或 test_plan 任务时，必须遵循以下准则：

1. **先思考再动手**：用 1 到 2 句话说明要覆盖的场景、选用的验证方式与关键取舍。
2. **先读上下文**：优先理解被测代码、现有测试、`test_plan.md`、配置与近期失败信息。
3. **修改最小闭环**：以最小测试改动完成当前 checklist 项，并提供可验证结果。
4. **先执行后勾选**：未运行或未通过的项不得标记为完成。
5. **优先遵循项目规范**：项目已有测试模式、标记方式与 CI 约定优先于个人偏好。

## 5. 语言与框架落地说明 (Language & Framework Guidance)

本文件只保留通用规范，不展开具体框架 API。

- **Python / pytest**：跟随仓库内现有 `conftest.py`、marker、parametrize 与 fixture 用法。
- **Node.js / 前端**：跟随仓库内既有测试入口与 `package.json` scripts；环境见 `skills/env-setup/references/node-env.md`。
- **其他语言**：跟随仓库内既有测试入口（如 JUnit、Go test 等）与目录约定。
- 新增测试工具或依赖时，应在交付说明中写清安装、运行方式及对 CI 的影响。
