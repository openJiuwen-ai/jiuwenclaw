# 需求分析原则

> 你需要作为**需求工程师**输出一份需求分析，本文档定义了针对Issue的需求分析方法论、流程规范和输出模板

## 1. 分析方法论

### 1.1 需求提取原则

- **完整性**: 确保所有需求都被识别和记录
- **准确性**: 准确理解用户的真实意图
- **一致性**: 需求之间不应存在矛盾
- **可验证性**: 每个需求都应该是可测试和可验证的
- **事实性**: 需求分析应基于Issue描述的事实和代码中可观察到的证据进行分析推理，允许基于已有信息进行合理推导（如从Bug现象推导受影响的功能模块、从代码结构推导依赖关系），但禁止无依据的猜测性推测（如未读代码就猜测根因、未分析就给出方案）。具体方案设计属于架构设计阶段的职责

### 1.2 需求分类标准

| 类型 | 标识关键词 | 优先级范围 |
|------|-----------|-----------|
| Bug | bug, 缺陷, 错误, 修复 | 高 |
| Feature | feature, 新功能, 支持, 新增 | 中 |
| Refactor | refactor, 重构, 优化 | 低 |
| Docs | docs, 文档, 说明 | 低 |

### 1.3 需求拆解原则

1. **单一职责**: 每个子功能点应该只负责一个明确的功能
2. **独立性**: 子功能点之间应尽量独立，降低耦合
3. **可测试性**: 每个子功能点都应该是可独立测试的
4. **可估算性**: 能够估算每个子功能点的工作量

### 1.4 协作澄清原则

**辅助 skill**：`skills/brainstorming/SKILL.md`（**调用主体为本子 agent**，Leader 不加载）。

本子 agent 补充：**§4.6 必须列出 2–3 条核心讨论项**；首轮落盘 `- [ ] **Q-xxx**` 并返回 `NEEDS_DISCUSSION`；收到 **澄清答复** 后勾选 `- [x]` 并填写「用户决定」。

### 1.5 Bug 根因分层原则（新增）

- **分层归因**：按 L0（呈现/Tool）→ L1（业务编排）→ L2（基础设施 IO/进程）→ L3（框架/OS）判断候选根因。
- **最少两层下探**：Bug 类分析默认沿调用链下探至少 2 层，不能只停留在返回字段或字符串拼装层。
- **机制优先于呈现**：先回答“数据/状态在哪一层丢失或失真”，再回答“返回给模型时如何展示”。
- **可审计证据**：在 SR 中记录根因层级与证据来源（代码路径/日志/行为对照）。
- **简单 Bug 例外**：若确认为 L1 逻辑错误，可不下探到 L2/L3，但须在文档显式写明理由与边界。

## 2. 分析流程

### 2.1 标准分析流程

```
探索上下文 → 识别讨论项 →（如需）先落盘 §4.6（`- [ ]`）→ Leader 澄清 → 勾选 `- [x]` 并回填用户决定 → 内容解析 → 类型判断 → Bug 分层归因（L0-L3）→ 需求提取 → 功能拆解 → 风险评估 → 文档定稿
```

### 2.2 分析检查清单

- [ ] Issue标题是否清晰明确
- [ ] Issue描述是否完整
- [ ] 是否包含复现步骤（Bug类型）
- [ ] 是否包含期望行为
- [ ] 是否包含相关日志或截图
- [ ] 是否已分配责任人
- [ ] 是否已设置优先级标签

### 2.3 讨论项识别检查清单

分析过程中持续自问（**仅 P0/P1/冲突**才提请 Leader，见 `skills/brainstorming/SKILL.md`）：

- [ ] 是否存在会改变 scope/验收/接口/数据模型的多种合理理解？若有，是否已写入 §4.6 或提请澄清？
- [ ] 验收标准是否可客观验证？若否且属 P0，是否已澄清？
- [ ] 范围边界（做/不做）是否明确？若否且属 P0/P1，是否已澄清？
- [ ] 代码证据与输入是否冲突？若冲突，是否已提请用户确认？
- [ ] Bug 类是否完成至少两层调用链下探，并记录根因层级（L0/L1/L2/L3）？
- [ ] 是否区分“机制修复”与“呈现修补”，避免把字段组装当成根因修复？
- [ ] Shell/IO 类是否覆盖 NFR：超时输出保真、超大输出、双流时序、进程清理、交互阻断？
- [ ] §4.6 是否已列出 2–3 条会改变 scope/验收/边界的核心问题？
- [ ] 有未决讨论项时 §4.6 是否均为 `- [ ]` 并已返回 `NEEDS_DISCUSSION`，且未误宣称 Gate/check 已通过？

## 3. 风险评估标准

### 3.1 风险等级定义

| 等级 | 描述 | 处理要求 |
|------|------|---------|
| 高 | 可能导致系统崩溃或数据丢失 | 必须立即处理，需要评审 |
| 中 | 影响核心功能或用户体验 | 需要在当前版本修复 |
| 低 | 影响非核心功能或边缘场景 | 可以在后续版本处理 |

### 3.2 风险识别关键词

- **安全风险**: 安全、权限、认证、加密、SQL注入、XSS
- **数据风险**: 数据库、数据迁移、数据备份、事务
- **性能风险**: 性能、并发、缓存、内存、CPU
- **兼容风险**: 兼容性、版本、升级、迁移

## 4. 输出结构与填写规范

> **结构唯一来源**：`references/requirements_template.md`。生成 `requirements.md` 时**复制该模板骨架**，再按下表填写；本章只规定「涉及性 / 必填项 / 禁忌」，不再重复模板正文。

### 4.1 章节涉及性

| 章节 | 涉及性 | 关键约束 |
|------|--------|---------|
| §1 背景与目标 / §2 需求澄清 / §3 需求条目(FR/NFR/AC) | 建议填写 | 概述来源、范围边界与可验证验收 |
| §4.1 初始需求澄清 | **所有类型必填** | §4.1.1 首段须有可见 `本次分析类型：<Type>`，与 `--type` 一致（不可仅写在注释中） |
| §4.2 功能性需求分析 | Feature/Bug 必填；Refactor/Docs 选填 | 不涉及字段标注「不涉及」，严禁编造；§4.2.9 只要有任一可能影响架构的方向就标「是/可能」 |
| §4.3 非功能性需求分析 | 仅涉及可靠性/可用性/安全时填 | Shell/IO 类建议补充「Agent/Shell 场景检查表」；不涉及可整章省略，严禁编造 |
| §4.4 功能影响列表 | **所有类型必填** | 至少 1 条真实记录，禁占位行，禁加不相关模块 |
| §4.5 系统分析列表 | **所有类型必填** | 4.5.2 至少 1 条真实 SR，禁占位；Bug 类应填写根因层级/证据来源/基础设施改动判断 |
| §4.6 协作讨论记录 | **所有类型必填** | 见下方「4.2 §4.6 协作讨论记录规则」 |

### 4.2 §4.6 协作讨论记录规则

- 列出 **2–3 条**核心讨论项（仅 P0/P1/冲突），每条须有「选项」与「建议默认」。
- **首轮**：全部 `- [ ]`，返回 `NEEDS_DISCUSSION`（`check_requirements.py` 预期失败，**勿**宣称 G1 PASS）。
- **定稿**：全部 `- [x]` 且填写真实「用户决定」；Agent **不得**以「默认决策」代填。
- 不得把「待确认事项 / Qn」清单写在 §4.6 之外的章节。

### 4.3 校验门禁（`check_requirements.py` 强制项）

- 必含且按序的标题：`### 4.1` → `### 4.4` → `### 4.5` → `### 4.6`（各唯一）。
- §4.1.1 含可见 `本次分析类型：<Type>`。
- §4.4 / §4.5.2 各至少 1 条非占位数据行。
- §4.6 共 2–3 条 `- [ ] **Q-xxx**`，定稿时全 `- [x]` 且「用户决定」非占位。
- 文档为 UTF-8 无 BOM。
- 可选增强：`--strict-layer` 开启后，Bug 类将对“根因层级/机制 AC/场景检查表”执行严格门禁。
