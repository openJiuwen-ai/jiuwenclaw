# 分层归因与反表层补丁指南

本指南用于统一 Aidlc 六阶段中的「根因层级 -> 设计深度 -> 任务顺序 -> 代码改动 -> 测试覆盖 -> 审查结论」对齐标准。

## 1. 分层模型

- L0：呈现与封装层（`*_tool.py`、formatter、返回体组装）。
- L1：业务与编排层（流程控制、状态管理、策略判断）。
- L2：基础设施层（IO、subprocess、进程生命周期、缓冲与持久化）。
- L3：框架/运行时/OS 行为（库实现、系统调用、信号与进程组语义）。

## 2. Bug 垂直追踪流程

1. 从用户可见现象出发，列出复现路径与观测点。
2. 沿调用链下探至少 2 层，形成候选根因列表（至少 2 个）。
3. 每个候选根因都标注证据来源（代码路径、日志、行为对照）。
4. 选择最可能根因层级，并说明为何排除其他层级。

## 3. 机制与呈现分离

- 先判断「数据/状态在何处丢失或扭曲」，再决定「如何展示」。
- 若只改 L0，而问题可能在 L2/L3，必须说明不下探的证据和风险。
- 禁止把字段补齐、字符串拼装当作机制修复的替代方案。

## 4. Agent 基础设施 NFR 清单（按需适用）

针对 Shell/Tool/Runner 类问题，优先检查：

- 超时/取消后输出保真（是否丢缓冲数据）。
- 超大输出策略（截断、持久化、预览、可追溯性）。
- stdout/stderr 时序语义（是否割裂上下文）。
- 超时后进程树清理（是否残留子进程）。
- 交互式命令阻断（如 sudo 密码等待导致挂起）。

## 5. PATCH_RISK 判定

满足任一条件可标记 `PATCH_RISK`：

- requirements 指向 L2/L3 根因，diff 仅在 L0。
- design 声明基础设施改造，dev_plan 或实现仅改组装逻辑。
- 测试只验证返回字段，未验证机制行为。

## 6. 讨论项模板建议（§4.6）

用于 analyzer/designer 阶段澄清：

- 方案 A：L0 快速补丁（低成本，风险高，可能掩盖根因）。
- 方案 B：L2 机制修复（成本高，稳定性与可维护性更好）。
- 需明确：本轮范围、风险接受条件、后续补偿计划。
