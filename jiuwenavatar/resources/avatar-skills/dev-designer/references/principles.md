# 架构设计原则

> 你需要作为**架构设计师**输出一份架构设计
>
> 本文档定义了针对Issue的架构设计方法论、设计原则和输出模板，参考《xxx服务组件实现设计说明书（模板）》

## 1. 设计原则

### 1.1 SOLID原则

- **单一职责原则 (SRP)**: 一个类应该只有一个引起它变化的原因
- **开放封闭原则 (OCP)**: 软件实体应该对扩展开放，对修改封闭
- **里氏替换原则 (LSP)**: 子类型必须能够替换它们的基类型
- **接口隔离原则 (ISP)**: 客户端不应该依赖它不需要的接口
- **依赖倒置原则 (DIP)**: 高层模块不应依赖低层模块，两者都应依赖抽象

### 1.2 架构设计原则

1. **模块化**: 系统应划分为独立的、可替换的模块
2. **分层架构**: 表现层、业务层、数据层应清晰分离
3. **高内聚低耦合**: 模块内部高度相关，模块之间松散耦合
4. **可扩展性**: 设计应考虑未来的扩展需求
5. **可维护性**: 代码应易于理解和修改

### 1.3 协作澄清原则

**辅助 skill**：`skills/brainstorming/SKILL.md`（**调用主体为本子 agent**，Leader 不加载）。

本子 agent 补充：**§协作讨论记录 必须列出 2–3 条核心讨论项**；首轮落盘 `- [ ] **Q-xxx**` 并返回 `NEEDS_DISCUSSION`；收到 **澄清答复** 后勾选 `- [x]` 并填写「用户决定」；可对决策点列 2–3 方案。

### 1.4 方案深度对齐原则（新增）

- **层级一致**：requirements 若定位为 L2/L3（基础设施/框架）根因，design 不得只给 L0/L1 表层拼装方案。
- **机制优先**：先设计机制修复（IO、进程、缓冲、取消语义），再设计返回渲染策略。
- **可追溯**：设计中的关键决策需明确映射到 requirements 的 SR/AC，不得凭经验越级跳结论。
- **可落地**：`## 实现注意事项` 必须列出预期文件修改清单，避免“只讲思路不落地”。

## 2. 模块划分标准

### 2.1 模块类型定义

| 模块类型 | 职责 | 依赖方向 |
|---------|------|---------|
| Core | 核心业务逻辑 | 被其他模块依赖 |
| API | 接口定义和处理 | 依赖Core |
| Database | 数据持久化 | 依赖Core |
| Auth | 认证和授权 | 依赖Core |
| UI | 用户界面 | 依赖API |
| Test | 测试用例 | 依赖所有模块 |

### 2.2 模块命名规范

- 模块名使用小写字母和下划线: `module_name`
- 类名使用大驼峰: `ModuleNameManager`
- 函数名使用小写字母和下划线: `function_name`
- 常量使用全大写和下划线: `CONSTANT_NAME`

## 3. 接口设计规范

### 3.1 接口定义原则

1. **明确性**: 接口应明确定义输入、输出和异常
2. **一致性**: 相似功能的接口应保持一致的命名和参数风格
3. **简洁性**: 接口应尽量简单，避免过多参数
4. **版本化**: 接口变更应考虑版本兼容

### 3.2 接口类型

| 类型 | 用途 | 示例 |
|------|------|------|
| REST API | HTTP接口 | GET /api/v1/users |
| RPC | 远程过程调用 | UserService.getUser() |
| Event | 事件接口 | onUserCreated() |
| CLI | 命令行接口 | python script.py --param |

## 4. 数据流设计

### 4.1 数据流原则

1. **单向流动**: 数据应单向流动，避免循环依赖
2. **数据验证**: 所有输入数据必须验证
3. **错误处理**: 每个数据流节点都应有错误处理
4. **日志记录**: 关键数据流节点应记录日志

### 4.2 标准数据流模式

```
输入 → 验证 → 转换 → 处理 → 格式化 → 输出
```

## 5. 技术选型标准

### 5.1 技术选型原则

- **成熟度**: 优先选择成熟稳定的技术
- **社区支持**: 选择有活跃社区支持的技术
- **团队熟悉度**: 考虑团队对技术的熟悉程度
- **性能**: 满足性能要求
- **可维护性**: 易于维护和扩展

### 5.2 技术栈推荐

| 领域 | 推荐技术 | 备选技术 |
|------|---------|---------|
| 语言 | Python 3.8+ | - |
| Web框架 | FastAPI | Flask |
| 数据库 | PostgreSQL | MySQL |
| 缓存 | Redis | Memcached |
| 测试 | pytest | unittest |
| 文档 | Markdown | reStructuredText |

## 6. 设计决策记录

### 6.1 决策记录模板

```markdown
## 决策标题

### 背景
描述决策的背景和问题

### 决策
描述做出的决策

### 理由
描述为什么做出这个决策

### 备选方案
列出考虑过的其他方案

### 影响
描述这个决策的影响范围
```

### 6.2 常见设计决策

1. **最小化修改范围**: Bug修复应尽量减少影响范围
2. **模块化设计**: 新功能应独立模块化
3. **渐进式重构**: 重构应分步骤进行
4. **安全评审前置**: 涉及安全问题的需先评审

### 6.3 讨论项识别检查清单

设计过程中持续自问（**仅 P0/P1/冲突**才提请 Leader，见 `skills/brainstorming/SKILL.md`）：

- [ ] 每个关键决策是否只有一种合理选择，或局部实现细节可默认定案？若否且影响验收/接口/数据模型，是否已提请讨论？
- [ ] requirements 中「待确认」SR 是否仍被设计假设覆盖？（禁止对 P0 未澄清项假设定案）
- [ ] 方案对比是否已给出权衡与推荐（brainstorming 方法）？
- [ ] §协作讨论记录是否已列出 2–3 条会改变 scope/验收/架构的核心问题？
- [ ] 有未决讨论项时 §协作讨论记录是否均为 `- [ ]` 并已返回 `NEEDS_DISCUSSION`，且未误宣称 Gate/check 已通过？

## 7. 输出结构与填写规范

> **结构唯一来源**：`references/design_template.md`。生成 `design.md` 时**复制该模板骨架**，再按下表填写；本章只规定「内容映射 / 涉及性 / 禁忌」，不再重复模板正文。
>
> 企业级详设（开发视图、运行视图、安全/算法子节等）应**折叠写入**下列 8 个落盘章节，**不得**另起 `### 7.x` 标题体系。

### 7.1 落盘章节与内容映射

| 落盘章节 | 应纳入的内容要点 | 涉及性 |
|---------|-----------------|--------|
| `# 设计文档` + `## 概述` | Issue 信息、设计目标、范围与约束 | **所有类型必填** |
| `## 概述` → `### 协作讨论记录` | 2–3 条核心讨论项 | **所有类型必填**；规则见 §7.2 |
| `## 架构` | 模块划分、分层、上下文/逻辑视图（可用 mermaid）、关键流程 | Feature/Refactor 必填；Bug 视情况；Docs 通常「不涉及」 |
| `## 组件和接口` | 组件职责、接口清单（含协议/入出参/错误码） | 有接口变更必填，否则「不涉及」 |
| `## 数据模型` | 实体、关系、存储/迁移策略（可用 mermaid ER） | 有数据结构变更必填，否则「不涉及」 |
| `## 正确性属性` | 不变量、等价关系、边界条件（**编号列出**） | **必填**；Bug/基础设施类至少一条机制级属性（如缓冲不丢、进程可清） |
| `## 错误处理` | 异常分类、失败模式、恢复/降级、安全与可靠性要点 | 视 Issue；无则简要说明 |
| `## 测试策略` | 可测试性、分层测试、关键场景与覆盖范围 | Feature/Refactor 必填；Bug 视情况 |
| `## 实现注意事项` | 决策摘要（D-xxx）、文件/模块修改清单、风险、依赖、上线回滚 | **所有类型必填**；需显式列出“文件修改清单” |

不涉及的子题在对应章节内写「不涉及」，**不得删除** `check_design.py` 要求的标题行。

### 7.2 §协作讨论记录规则

- 位于 `## 概述` 下，标题须为 `### 协作讨论记录`。
- 列出 **2–3 条**核心讨论项（仅 P0/P1/冲突），每条须有「选项」与「建议默认」。
- **首轮**：全部 `- [ ]`，返回 `NEEDS_DISCUSSION`（`check_design.py` 预期失败，**勿**宣称 G2 PASS）。
- **定稿**：全部 `- [x]` 且填写真实「用户决定」；Agent **不得**以「默认决策」代填。
- 不得把「待确认事项 / Qn」写在协作讨论记录之外的章节。
- requirements 中 P0 未澄清的 SR **禁止**在设计中假设定案。

### 7.3 校验门禁（`check_design.py` 强制项）

- 上游 `requirements.md` 已存在。
- 必含且按序：`# 设计文档` → `## 概述` → `## 架构` → `## 组件和接口` → `## 数据模型` → `## 正确性属性` → `## 错误处理` → `## 测试策略` → `## 实现注意事项`。
- `## 概述` 下含 `### 协作讨论记录`，共 2–3 条；定稿时全 `- [x]` 且「用户决定」非占位。
- 文档为 UTF-8 无 BOM。
